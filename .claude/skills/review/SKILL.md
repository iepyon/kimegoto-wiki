# 確認② — 25分の判定

共通規約は `CLAUDE.md` が正典。以下は本スキル固有の手順。

## 最重要の制約

> **`なぜ` と却下理由を書いてはならない。**
>
> 文字起こしを読んで合成した理由は一見正しく、人間が通してしまう。
> これがこの仕組みの最大の失敗モードである。
> 人間が実際に言った言葉だけを書き込む。書けなければ `記録なし` を入れる。

推測を補助として差し出すこともしない。「〜ということでしょうか」と水を向けると、
相手はそれを追認してしまう。**開いた問いで聞く。**

## 手順

1. `python3 tools/giji.py review --meeting MTG-YYYYMMDD` を実行する
2. 出力の 2-0 → 2-4 の順に、**該当するカードだけ**を人間に提示する
3. 各項目は `AskUserQuestion` で聞き、**返ってきた言葉をそのまま**書き込む
4. 終わったら `python3 tools/giji.py lint` で error 0 を確認する

## 順序と時間配分

| | 内容 | 目安 | 聞き方 |
|---|---|---|---|
| 2-0 | `範囲: 判定保留` の決定 | 3分 | 「当初の合意に入っていましたか、追加ですか、まだ判断できませんか」 |
| 2-1 | `信頼度: 推測` のカード | 4分 | 「これは実際にそう言われましたか」 |
| 2-2 | 決定の `なぜ` | 8分 | 「なぜこの案にしたのですか」（Y-statement の穴埋めは**雛形として見せるだけ**） |
| 2-3 | アクションの担当・期限・status | 4分 | 「どこの会社が、いつまでに」 |
| 2-4 | 昇格候補の承認 | 6分 | yes / no だけ |

**2-4 に入る前に Pass 4（`/promote`）を回す。** `giji promote-input` は `なぜ` が
未記入の決定を材料から落とすので、2-2 より前に回すと材料が空になる。
順序は 2-2（なぜ）→ `/promote` → 2-4（承認）。

2-0 は受託開発では最優先。他を飛ばしてもここは見る。
無理に判定すると、後で追加請求の根拠を失う。

## 埋まらなかったときの扱い

- `なぜ` が出てこない → **空欄のまま残す。** 次回アジェンダに掲示される
- 却下理由を思い出せない → `記録なし` を入れる
- 担当・期限が決まっていない → 空欄のまま。次の定例で埋める

全部書けなくてよい。1つでも埋まれば空欄より価値がある。

## 承認者を限定しない

「リーダの承認が要る」といった運用をここに足さない。
最初は承認ゼロで回し、矛盾検出が効き始めてから足す。
