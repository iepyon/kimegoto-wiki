# 確認② — 25分の判定（Pass 4 を含む）

共通規約は `CLAUDE.md`、根拠は `research-notes.md` が正典。以下がこのパスの判定基準。

昇格（Pass 4）をこのスキルに含めているのは、**回す順番を間違えると材料が空になる**から。
`kime promote-input` は理由がどこにも記録されていない決定を材料から落とすので、
`なぜ` を書く 2-2 より前に回すと何も出ない。順番を2つのファイルに分けて持つと必ずずれる。

## 最重要の制約

> **`なぜ` と却下理由を書いてはならない。**（`CLAUDE.md` のルール1）

推測を補助として差し出すこともしない。「〜ということでしょうか」と水を向けると、
相手はそれを追認してしまう。**開いた問いで聞く。**

## 手順

1. `python3 tools/kime.py review [--meeting MTG-YYYYMMDD]` を実行する
   （指定が無ければ最新の会議。`kime status` の「確認②」の行が該当件数）
2. 出力の 2-0 → 2-3 の順に、**該当するカードだけ**を人間に提示する
3. 各項目は `AskUserQuestion` で聞き、**返ってきた言葉をそのまま**書き込む。
   2-0 の判定は決定の `範囲` に書く（`kime update DEC-NNN --set 範囲=…`）。Q は立てない・閉じない
   （`判定保留` のあいだ「範囲の確認」として射影されているだけなので、書けば消える）
4. 2-3 が終わったら `python3 tools/kime.py promote-input --meeting MTG-YYYYMMDD` を回し、
   下記に従って候補を挙げ、`meetings/MTG-YYYYMMDD/promote-candidates.yaml` に書き出す
5. 2-4 で候補を yes/no で承認してもらい、**承認されたものだけ**を
   `constraints/` `assumptions/` `terms/` にカードとして作る
6. 2-5 でこの会議の議題が決着したかを聞き、返ってきた判定だけを
   `kime update AGD-NNN --set status=… --set 決着日=<会議日>` で書く（閉じた日を残す）
7. `python3 tools/kime.py lint` で error 0 を確認する

順序は **2-2（なぜ）→ promote-input → 2-4（承認）**。ここを崩さない。

## 順序と時間配分

時間配分と該当カードの一覧は `kime review` が出す。ここには**聞き方**だけを置く。

| | 内容 | 聞き方 |
|---|---|---|
| 2-0 | `範囲: 判定保留` の決定 | 「当初の合意に入っていましたか、追加ですか、まだ判断できませんか」 |
| 2-1 | `信頼度: 推測` のカード | 「これは実際にそう言われましたか」 |
| 2-2 | 決定の `なぜ` | 「なぜこの案にしたのですか」（Y-statement の穴埋めは**雛形として見せるだけ**） |
| 2-3 | アクションの担当・期限・status | 「どこの会社が、いつまでに」 |
| 2-4 | 昇格候補の承認 | yes / no だけ |
| 2-5 | 議題の締め | 「この議題は決着しましたか、次回も続けますか、取り下げますか」（`目安` は見せるだけ） |

2-5 で未決の問いが残っている議題は決着にしない（lint の `agd-closed-open` が鳴る）。
**結論が出なかった議題は何もしない。** 開いたまま次回へ持ち越され、アジェンダには
「扱ったが結論なし」と出る。`決着候補` と出ていても、決めるのは人間。

2-0 は受託開発では最優先。他を飛ばしてもここは見る。
無理に判定すると、後で追加請求の根拠を失う。

## 埋まらなかったときの扱い

- `なぜ` が出てこない → **空欄のまま残す。** 次回アジェンダに掲示される
- 却下理由を思い出せない → `記録なし` を入れる
- 担当・期限が決まっていない → 空欄のまま。次の定例で埋める

全部書けなくてよい。1つでも埋まれば空欄より価値がある。

## 承認者を限定しない

「リーダの承認が要る」といった運用をここに足さない。
最初は承認ゼロで回し、矛盾検出が効き始めてから足す。

# Pass 4 — 昇格候補の提示

ストック層への昇格候補を提示する。**この段階ではカードを作らない。**
承認を得てから 2-4 で作る。

## 出す問いは4種類だけ

| # | 問い | 対象 |
|---|---|---|
| 1 | 「この却下理由は既存の CON-NNN と同じ内容です。紐づけますか」 | 既存制約への紐づけ |
| 2 | 「この却下理由は他の決定にも効きそうです。制約として切りますか」 | 新規制約の昇格 |
| 3 | 「この決定に条件が付いています。前提として切りますか」 | 新規前提の昇格 |
| 4 | 「未知語が N 件あります。用語にしますか」 | 用語の昇格 |

候補の上限は材料の末尾に出る。**根拠の強い順にそこまで。**
取りこぼしても次回以降に拾えるので、量より確度を優先する。

## 昇格の門は入力の時点で閉じている

**理由がどこにも記録されていない DEC から生えた候補は出さない。** 理由が記録されて
いない制約は、将来の議論で参照されても判断材料にならない。

門を通る条件は `なぜ` **または** `代替案[].却下理由` のどちらかがあること。
CON の中身は「採った案の理由（`なぜ`）」ではなく「捨てた案の理由（`却下理由`）」
なので、`なぜ` だけで閉じると、逐語で却下理由が取れている制約まで落ちる。
どちらも `記録なし` は記録として数えない（「記録なし」と答えても空欄でも、門は同じ）。

例外は `種別: 契約制約` の決定。契約・法務の決定は、決定そのものが環境の性質を
述べていることが多いので、理由が無くても決定の引用が材料に出る
（「契約制約の決定（役割）: 引用」の行）。制約として切るかは、下の判定のとおり。

`kime promote-input` が該当する決定を**材料そのものから落とす**。注意書きではなく入力の
欠落で守っている。落とされた決定は材料の末尾に一覧で出るので、人間に伝える。

## 1・2 — 制約の判定

まず**自社で守れるかを問う**。守れるものは CON でも ASM でもない。

```
その制約は、自社の作業で守れるか？
├ 守れる                       → 候補に出さない（ACT か DEC の領域）
└ 守れない
   ├ 環境の事実（法令・物理・既存システムの仕様）
   │    → CON（種類: property）／失効条件は「該当なし」でよい
   ├ 相手方に割り当てた期待（顧客が〜してくれる）
   │    → CON（種類: expectation）／失効条件が必要
   └ 単に成り立っていればよい仮定（利用者は50人規模）
        → ASM（問い3へ）
```

根拠は「assumptions cannot be enforced by the software-to-be」（KAOS）。

次に**その決定に固有か、環境の性質か**を問う。

| 却下理由の例 | 判定 |
|---|---|
| 「この案は工数が合わない」「今回のスケジュールに間に合わない」 | 固有。**昇格しない** |
| 「顧客側VPNが固定IPのみ」 | 環境の性質。**昇格** |
| 「基幹システムがShift-JISしか受け付けない」 | 環境の性質。**昇格** |
| 「情シスの承認が四半期に1回しか下りない」 | 環境の性質。**昇格** |

**迷ったら昇格させない。** 同じ理由が2つ目の決定に現れた時点で昇格すればよく、1回目で
見抜く必要はない。既存の制約と内容が実質同じなら、新規ではなく問い1（紐づけ）として出す。
判断がつかなければ両方を並べて人間に選ばせる。

```yaml
  - 種別: 新規制約
    内容: 顧客側VPNは固定IPのみ
    種類: expectation               # property | expectation
    根拠: DEC-014 の却下理由
    引用: ADに繋ぐのは、まあVPNが固定IPなんで厳しいですね
    derived_from: LOG-20260918-03
    失効条件: 不明                  # property なら「該当なし」。手掛かりが無ければ「不明」
    影響しそうな既存の決定: [DEC-009]  # 確信がなければ空
```

**`所在` と `硬度` は書かない。** 承認後に
`kime new constraint --from-log LOG-... --role <発言した役割> --kind <種類>` が
role-mapping と導出表から埋める。`引用` には候補の引用をそのまま写し、`信頼度` は
`逐語あり` にして `kime verify-quotes --fix` に照合させる（一致しなければ `推測` に降格する）。

## 3 — 前提の検出

トリガー語（「今は」「当面」「現状」「一旦」など）の走査は `kime promote-input` が
済ませており、該当する決定が材料に一覧で出る。**自分で語を探さない。**
出ている決定について、前提として切るかどうかだけを判断する。

前提カードの本体は内容ではなく**逆リンク**。

```yaml
  - 種別: 新規前提
    内容: 当面の利用者は50人規模
    崩れたら見直す決定: [DEC-014]    # ← 必須。空なら候補として出さない
    脆弱性: 高                      # 高 | 中 | 低
    signpost: 不明                  # 事象または閾値。発言に無ければ「不明」
    引用: はい、当面はその規模です
    derived_from: LOG-20260918-03
```

**`崩れたら見直す決定` が特定できない前提は候補に出さない。** 逆リンクのない前提カードは
飾りになる。

`脆弱性` は「覆されやすさ」。

| 値 | 基準 |
|---|---|
| `高` | プロジェクト期間内に変わる見込みがある（利用者数、組織体制、他システムの更新予定） |
| `中` | 変わり得るが時期の見込みがない |
| `低` | 期間内に変わるとは考えにくい |

**運用対象は `脆弱性: 高` のものだけ。** 全件追跡は2週25分では破綻する。

`signpost` は **事象または閾値**でなければならない。

- ✗ 「利用者数に注意する」— 事象でも閾値でもない
- ○ 「月次報告の利用者数が80人を超える」— 閾値
- ○ 「顧客の組織改編が発表される」— 事象

**取れない場合は `不明` と書く。推測で作らない。** ②で埋まらなければ `脆弱性` を `中` に
落とすのが正しい扱い（追跡できない前提を運用対象にしない）。

## 4 — 用語の判定

Pass 2 の未知語リスト（`meetings/*/unknown-terms.yaml`）を既存の用語集と照合して3つに分ける。

| 分類 | 提案 |
|---|---|
| 既存用語の表記崩れ | 既存 TERM の `表記揺れ` への**追記** |
| 新規用語 | 新規 TERM カードの作成 |
| 一般語・判断不能 | 候補から除外 |

```yaml
  - 種別: 表記揺れの追記
    対象: TERM-012
    追加する表記: [オイデッシー]
    出現回数: 4
    根拠: TERM-012 の読み「オーアイディーシー」に音が近い

  - 種別: 新規用語
    正式: 権限マトリクス
    定義案: 不明                    # 会議で定義が語られていなければ「不明」
    初出: LOG-20260918-05
    出現回数: 3
```

表記揺れの追記は最も効果が高い（次回の正規化精度が上がり、引用検証の通過率が上がる）。
出現回数が閾値に届かなくても、既存用語の崩れと判断できるなら提案してよい。

## Pass 4 の禁止事項

- 承認前にカードファイルを作成・更新する
- 4種類以外の提案をする（「この決定は見直すべき」等の意見を書かない）
- `失効条件` `signpost` `定義案` を推測で埋める（`不明` を使う）
- `崩れたら見直す決定` が空の前提を候補に出す
- 固有の事情（工数・スケジュール）を制約として昇格させる
- `所在` `硬度` を手で書く（`kime new` が導出する）

## 四半期ごとの前提の棚卸し（年4回・5分）

②とは別の運用。`python3 tools/kime.py views` の `open-items.md` が対象を抜き出す。

```
status: 有効 かつ 脆弱性: 高 の前提について、signpost が発火していないかだけを見る。

崩れていた場合:
  1. status を「崩れた」に変更
  2. 「崩れたら見直す決定」の DEC をすべて確認
  3. 見直しが必要な DEC は status を「保留」にして Q を起票
```

制約は破ろうとした時に気づくが、前提は誰にも気づかれずに崩れる。定期的な棚卸しだけが
検出手段になる。
