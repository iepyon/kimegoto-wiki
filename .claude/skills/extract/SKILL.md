# Pass 3 — DEC / Q / ACT の抽出

共通規約は `CLAUDE.md`、何を DEC とするかは `decision-guide.md`、設計の根拠は
`docs/design.md`。以下がこのパスの判定基準。

**CON / ASM / TERM はこのパスで作らない**（Pass 4 の人間承認を経たものだけが存在する）。
ストック層は寿命が長く、誤りのコストが桁で違う。

## 必ず1論点ずつ処理する

**全論点を一度に渡さない。** コンテキストが伸びると逐語引用が要約され始め、引用が崩れる。
引用が崩れると検証機構が死ぬ。

各回に読むもの: LOG カード1枚／その `種別` と会議内の位置（第何セグメント・全何セグメント）／
`role-mapping.yaml`／`decision-guide.md`／既存 `questions/*.md`・`actions/*.md` の id と title。

**`種別` と位置を必ず見る。**「会議のどの局面か」は話者情報より強い信号になる。
役割ルールを単独の決め手にしない。

## 手順

1. `python3 tools/kime.py status` で対象の会議と、抽出が残っている論点を見る
   （会議の指定が無ければいまの会議。途中からなら「残り」の論点だけをやる）。
   `python3 tools/kime.py lint --check log-format` で LOG の形式を確認
2. `種別` が `報告` / `雑談` なら **DEC は抽出しない**（ACT と Q のみ）。
   ただし決定権のある役割の結論の表明（「そのあたりは任せます」など）が現れたら、
   **Q として拾う**（下の「報告・雑談での取りこぼし」）
3. 下記に従い、1論点ずつ抽出する
4. カードを作る。**導出フィールドは自分で書かない**（下記）

   ```
   python3 tools/kime.py new decision --title "..." \
       --from-log LOG-20260918-03 --role 顧客PM --write
   ```

5. `python3 tools/kime.py verify-quotes --fix` → `kime lint` で error 0 を確認
6. 人間の確認は `/review` が進行する（このスキルでは求めない）

## 非対称に設計する

**迷ったら DEC ではなく Q か LOG に落とす。そして候補は多めに出す。**

嘘の DEC は半年後まで残り、それを根拠に仕様が書かれる。余分な Q は次回定例で消える。
害の大きさが違うので、判断を DEC 側に寄せない。

同時に**高再現・低精度に振る**。「拾いすぎて人が捨てる」が機械の得意な形で、逆向き
（精度を上げて人が足す）は機械も人間も苦手。

1. **決定権のない役割の発言だけでは DEC を起票しない。必ず Q に落とす**
2. 引用できる発言がない決定は起票しない
3. 「決まりそうだった」「そういう流れだった」で起票しない
4. **迷ったものは捨てずに Q として出す**（人間が捨てる前提）

## 欠落ガード

会議要約のエラーは**欠落が幻覚の3倍以上多い**。そして引用検証は「言っていないことを
言った」を捕まえるが「**言ったことを落とした**」を一切検出しない。だからここで守る。

> **`種別` が `議論` / `確認` のセグメントでは、DEC / Q / ACT を合わせて最低1件出す。
> 出せない場合は理由を1行書く。**

書き先は `meetings/MTG-YYYYMMDD/extraction-notes.yaml`。
LOG は不変層で後から書き足せず、理由はカードでもないので、会議ごとの別ファイルに置く。

```yaml
meeting: MTG-20260918
notes:
  - log: LOG-20260918-01
    extraction_empty_reason: 前回の決定内容の読み上げのみで、新たな判断は現れなかった

  - log: LOG-20260918-06
    review_required: true
```

理由が書けない、または「特になし」に留まるなら `review_required: true` を立てる。
`報告` / `雑談` は0件でよい（理由も不要）。

`lint` の `log-barren` は、理由が書かれている LOG を鳴らさない。
`review_required: true` は「判断がついていない」という記録なので鳴らし続ける。

## 報告・雑談での取りこぼし

`報告` / `雑談` で DEC を抽出しないのは、粒度の判定（Pass 1）を信じるからだが、
**トピック分割は境界の約3割が誤る**（`docs/design.md` の「期待値の較正」）。
`議論` が `報告` に落ちた回は、その論点の決定がまるごと消える。

そこで、`報告` / `雑談` でも次だけは拾う。

> **決定権のある役割が結論を述べていたら、DEC ではなく Q として起票する。**
> title は「〈結論の内容〉を決定として扱ってよいか」、確認先はその役割。

DEC にしないのは、`種別` の判定と衝突させないため。Q なら次回定例で消えるので、
誤起票の害は小さい（「迷ったら DEC ではなく Q」と同じ非対称）。
`decision-guide.md` の境界例（「そのあたりは任せます」＝判断の委任そのものが決定）が、
`報告` の中に現れたときの逃げ道がこれ。

## 役割別の解釈ルール

`role-mapping.yaml` で `所属` × `決定権` に引き当ててから解釈する。

| 発言パターン | 顧客側・決定権あり | 自社側・決定権あり | 決定権なし |
|---|---|---|---|
| 「じゃあ〜で」「〜でいきましょう」 | **DEC 確定** | DEC（技術判断） | **Q に落とす** |
| 「今回はスコープ外」「次フェーズで」 | DEC（`作らない` に記入） | DEC + Q を併記（顧客承認待ち） | Q |
| 「一旦置いといて」「保留で」 | Q（確認先=その役割） | Q | LOG のみ（提案の取り下げ） |
| 「〜だと厳しい」「〜がネック」 | Pass 4 へ制約候補 | Pass 4 へ制約候補 | LOG のみ |
| 「〜やっておきます」 | ACT（担当=その役割の社名） | ACT | ACT |
| 「〜という手もある」 | 代替案の言及として記録 | 同左 | 同左 |

**アクションだけは決定権を問わない。** 誰が言っても約束は約束。

論点に `議題` が付いていて、その議題に結論が出なかった場合は、下の「議題に出したが
結論が出なかったとき」が**この表より優先する**。決定権のない役割の「じゃあ〜で」が
議題そのものの答えなら、Q に落とさない（開いたままの議題が「まだ決まっていない」を
表している。Q にすると議題の言い換えになる）。

## 引用はどの発話から採るか

| 優先 | 種類 | 例 | 性質 |
|---|---|---|---|
| 1 | 合意 | 「はい、それでいきましょう」 | 決定文として最も安定 |
| 2 | 復唱 | 「じゃあ OIDC の方向で、ということで」 | 安定。照合が通りやすい |
| 3 | 提案 | 「OIDC に寄せる手もあります」 | **言い換えられ、撤回される** |
| — | 論点提示 | 「認証方式どうしましょう」 | Q の引用に使う |

提案発話を DEC の `引用` に使うと「それは提案にすぎなかった」という争いになる。
**合意・復唱があればそれを採る。** 無ければ提案発話でよく、`信頼度` は照合結果に従う。

## 沈黙の扱い — 無条件で `推測`

決定権のある役割が結論を述べ、異論なく次の論点に移った場合、DEC にしてよい。ただし
**`信頼度: 推測` を固定**する。代替案の却下を沈黙から判定した場合も同じ。

沈黙を却下のシグナルとして使う手法は文献に対応するものがない。明示的な合意ですら
人間の一致率も自動検出も最も難しいクラスで、沈黙はそれより弱い根拠でしかない。

`言及のみ` は「代替案の言及の引用は取れたが、却下理由の発言がない」場合に限る。

## 却下パターンの検出

```
段階1  代替案の言及   「〜という手もある」「〜でもいいんだけど」「〜も考えたんですが」
段階2  否定的な反応   「うーん」「それだと〜」「〜が厳しい」／または沈黙
段階3  別案への移行   「じゃあ〇〇で」
```

### 段階1だけのケース — ここが最も価値が高い

**段階2・3がなく、代替案が言及されたまま流れた場合も必ず記録する。**

```yaml
代替案:
  - 案: 自社でID基盤を実装
    却下理由: 記録なし
    引用: 自前で作る手もあるんですけどね
    信頼度: 推測              # 沈黙を根拠にしたので 推測 固定
```

反応が沈黙ではなく明示的な否定発話なら、その発話を却下理由の引用にして `信頼度` は
照合結果に従う。

**これが最も価値の高い抽出対象。** 半年後の「あの案はなぜやらなかったのか」に
「**そもそも検討されずに流れた**」と答えられる。議事録には100%残らない。**捨てないこと。**

却下理由が発言として存在しないなら、**推測して書かず** `記録なし` を入れる。

## 振り分けの決定木

```
発言が…
├ 期限または担当が伴う約束              → ACT
├ 決定権のある役割による結論の表明       → DEC（同じ論点の代替案は DEC の中へ）
├ 結論が出ていない／誰かの回答待ち       → Q
├ 選択肢を削る環境の性質                → DEC の却下理由に書く（CON は Pass 4）
├ 条件付きの前提（「今は」「当面」）      → DEC の `なぜ` に書く（ASM は Pass 4）
└ 上記いずれでもない                    → 何も作らない（LOG に残っていればよい）
```

**「何も作らない」を恐れない。** 1つの論点から DEC が0件でも正常。

## 既存 Q / ACT との同一性判定

- 同じ問い・同じ約束が再度議論されているなら、**新規作成せず更新差分を出す**
- 確信が持てないなら**新規として起票し `同一性候補: [Q-031]` を付けて人間に委ねる**
- Q が解決したら、対応する DEC の id を `resolved_by` に入れる
- 既存カードの `議題` は付け替えない（議題が変わったなら、それは別の問い）

## 議題に出したが結論が出なかったとき

**議題そのものを Q に立てない。** 開いたままの議題が「まだ決まっていない」を表している
（次回へ自動で持ち越される）。同じ問いを Q にすると二重になる（lint の `q-restates-agenda`）。

- 決まらなかった理由・待っている相手が発言に出た → その**足りないもの**を Q にする
  （「費用は持ち帰って確認します」→ 「追加費用をどう扱うか」、確認先はその発言者）
- 「次回また」で終わった、理由が発言に無い → **何も起票しない。** 理由を推測で書かない

精度は用語集の充実度に依存する。最初の数回は誤りが多い前提で、必ず候補を明示する。

## 出力形式

新規カードは `schema.md` の定義に従い frontmatter 完備で。既存カードの更新は差分のみ。

```yaml
updates:
  - id: Q-031
    status: 解決
    resolved_by: DEC-014
    最終言及: 2026-09-18
```

## `スコープ` の判定（受託開発では必ず立てる）

`種別`（今後変えられるか）と**直交する軸**なので、両方を必ず入れる。

- 発話に「当初の要件に入っていた／いない」の明示があればそれに従う
- **明示がなければ無条件で `判定保留`。推測して判定しない**

**`判定保留` の決定に Q を立てない。** `スコープ: 判定保留` そのものが「まだ顧客に聞いていない」を
表し、アジェンダと議事録に「スコープの確認」として機械が射影する（`kime scope-questions` で一覧できる）。
文面も確認先も一意に決まるので、自分で書かない。スコープは契約の問いで、議題を決める材料ではない。

ここで無理に判定すると、後で追加請求の根拠を失う。スコープは `判定保留` のまま残し、
②の 2-0 で人間が見る（`kime review` が最初に出す）。

## 機械が埋めるもの、空欄のまま残すもの

`決定の所在` / `会議体` / `種別` / `担当` / `所在` / `硬度` / `derived_from` / 日付、
そして `議題` は `kime new --from-log --role` が role-mapping・会議メタ・`segments.yaml` から
埋める。**自分で書かない。**
一意に決まる写像なので、手で書けば取り違えるだけ損をする。役割が未登録のとき、
決定権が「あり」でないときはコマンドが標準エラーに注意を出す。**その注意に従う。**

`なぜ` / 却下理由 / `スコープ` / ACT の `担当`・`期限` は、発話に明示がなければ**空欄のまま**。
推測で埋めない。抽出の難易度は一貫して 本文 > 担当 > 期限 の順で、ここは人間が②で埋める。
**空欄が正常な出力。**

## 引用の書き方

- LOG カード本文から**文字単位で正確に**コピーする。前後を削るのは可、語を変えるのは不可
- 鉤括弧は付けない。1発言から1引用（複数発言にまたがらない）
- トピック分割は境界の約3割が誤るので、**隣接セグメントの LOG から引用してよい**。
  その場合 `derived_from` に両方の id を入れる

引用は機械検証され、一致しないものは `信頼度: 推測` に強制降格される。整えて書くと
降格するだけなので、原文のまま写す。

## 禁止事項

- 却下理由・`なぜ` を推測して書く（`記録なし` / 空欄を使う）
- CON / ASM / TERM を作る
- 複数論点をまとめて処理する
- 引用を整える・要約する
- 決定権のない役割の発言から DEC を起票する
