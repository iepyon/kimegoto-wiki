# Pass 4 — 昇格候補の提示

## このパスの役割

ストック層（制約 CON / 前提 ASM / 用語 TERM）の昇格候補を提示する。

**カードを作成しない。** 候補を提示し、人間の yes/no を待つ。
ストック層は会議をまたいで生き続けるため、誤りのコストがフロー層と桁で違う。
必ず人間の承認を通す。

全体を見る必要があるため、Pass 3 の全出力が揃ってから1回だけ実行する。

---

## 入力

- Pass 3 の全出力（今回の会議で生成・更新された DEC / Q / ACT すべて）
- `constraints/*.md` — 既存の制約すべて
- `assumptions/*.md` — 既存の前提すべて
- `terms/*.md` — 既存の用語すべて
- `meetings/MTG-YYYYMMDD/unknown-terms.yaml` — Pass 2 の未知語リスト

## 出力

- `meetings/MTG-YYYYMMDD/promote-candidates.yaml`

---

## プロンプト本体

以下をそのまま指示として渡す。

---

あなたはストック層への昇格候補を提示する。カードは作らない。

### 出す問いは4種類だけ

余計な提案をしない。次の4つ以外は出力しない。

| # | 問い | 対象 |
|---|---|---|
| 1 | 「この却下理由は既存の CON-NNN と同じ内容です。紐づけますか」 | 既存制約への紐づけ |
| 2 | 「この却下理由は他の決定にも効きそうです。制約として切りますか」 | 新規制約の昇格 |
| 3 | 「この決定に条件が付いています。前提として切りますか」 | 新規前提の昇格 |
| 4 | 「未知語が N 件あります。用語にしますか」 | 用語の昇格 |

---

### 昇格の前提条件（門1）

**`なぜ` が未記入の DEC から生えた候補は、昇格候補に出さない。**

理由が記録されていない制約は、将来の議論で参照されても判断材料にならない。
これは必須フィールドを作らずに `なぜ` の記入を促すための仕掛けでもある
（書かないと、その制約が将来の議論で自動的に効かない）。

### 1・2 — 制約の判定基準

まず**自社で守れるかを問う**。守れるものは CON でも ASM でもない。

```
その制約は、自社の作業で守れるか？
├ 守れる                       → 候補に出さない（ACT か DEC の領域）
└ 守れない
   ├ 環境の事実（法令・物理・既存システムの仕様）
   │    → CON（種類: property）／失効条件は「該当なし」でよい
   ├ 相手方に割り当てた期待（顧客が〜してくれる）
   │    → CON（種類: expectation）／失効条件が必要
   └ 単に成り立っていればよい仮定（利用者は50人規模）
        → ASM（問い3へ）
```

根拠：「**assumptions cannot be enforced by the software-to-be**」（van Lamsweerde 2001, KAOS）。

次に**その決定に固有か、環境の性質か**を問う。

| 却下理由の例 | 判定 |
|---|---|
| 「この案は工数が合わない」 | 固有。**昇格しない** |
| 「今回のスケジュールに間に合わない」 | 固有。**昇格しない** |
| 「顧客側VPNが固定IPのみ」 | 環境の性質。**昇格** |
| 「基幹システムがShift-JISしか受け付けない」 | 環境の性質。**昇格** |
| 「情シスの承認が四半期に1回しか下りない」 | 環境の性質。**昇格** |

**迷ったら昇格させない。** 同じ理由が2つ目の決定に現れた時点で昇格すればよい。
1回目で見抜く必要はなく、取りこぼしのコストは低い。

既存の制約と内容が実質同じなら、新規ではなく問い1（紐づけ）として出す。
表現が違っても内容が同じなら紐づけを提案する。判断がつかなければ両方を並べて人間に選ばせる。

#### 昇格候補に含める情報

```yaml
  - 種別: 新規制約
    内容: 顧客側VPNは固定IPのみ
    種類: expectation               # property | expectation
    所在: 顧客側                    # 発言した役割の所属から自動
    硬度: 沈殿                      # 種類 × 所在 から自動（下表）
    根拠: DEC-014 の却下理由
    引用: ADに繋ぐのは、まあVPNが固定IPなんで厳しいですね
    derived_from: LOG-20260918-03
    失効条件: 不明                  # property なら「該当なし」。発言に手掛かりが無ければ「不明」
    影響しそうな既存の決定: [DEC-009]  # 内容から推定。確信がなければ空
```

硬度は入力せず `種類` × `所在` から機械的に決める。

| 種類 | 所在 | 硬度 |
|---|---|---|
| property | 契約 / 法令 | 岩盤 |
| property | 顧客側 / その他 | 沈殿 |
| expectation | 顧客側 | 沈殿 |
| expectation | 自社側 / 協力会社 | 懸濁 |

`失効条件` は `property` なら `該当なし`（事実は失効しない）。
`expectation` で発言に手掛かりがなければ `不明` とする。**推測して書かないこと。**

---

### 3 — 前提の検出トリガー

DEC の `なぜ` および却下理由の中に次の語が現れたら、必ず前提の候補として出す。

```
今は / 当面は / 〜のうちは / 現状 / いまのところ / 今回は / 初期は /
とりあえず / 一旦 / 今のフェーズでは / 〜規模なので
```

前提カードの本体は内容ではなく**逆リンク**である。必ず次を埋める。

```yaml
  - 種別: 新規前提
    内容: 当面の利用者は50人規模
    崩れたら見直す決定: [DEC-014]    # ← 必須。空なら候補として出さない（load-bearing）
    脆弱性: 高                      # 高 | 中 | 低（vulnerable）
    signpost: 不明                  # 事象または閾値。発言に無ければ「不明」
    次回確認日: 2026-10-02           # 既定値＝次回会議日
    引用: はい、当面はその規模です
    derived_from: LOG-20260918-03
```

**`崩れたら見直す決定` が特定できない前提は候補として出さない。**
逆リンクのない前提カードは飾りになる。

#### `脆弱性` の判定

Assumption-Based Planning は前提を **load-bearing**（計画がそれに依存）と
**vulnerable**（覆されやすい）の2軸で絞る。逆リンクが前者、`脆弱性` が後者。

| 値 | 基準 |
|---|---|
| `高` | プロジェクト期間内に変わる見込みがある（利用者数、組織体制、他システムの更新予定） |
| `中` | 変わり得るが時期の見込みがない |
| `低` | 期間内に変わるとは考えにくい |

**運用対象は `脆弱性: 高` のものだけ。** 中・低は記録するが四半期棚卸しの対象にしない。
全件追跡は2週25分では破綻する。

#### `signpost` — 事象または閾値でなければならない

「検知方法」の標準名は **signpost**。定義は

> an event or threshold that, if detected, signifies that a vulnerable assumption is being broken
> （Walker, Haasnoot & Kwakkel 2013 / Assumption-Based Planning, RAND）

- ✗ 「利用者数に注意する」— 事象でも閾値でもない
- ○ 「月次報告の利用者数が80人を超える」— 閾値
- ○ 「顧客の組織改編が発表される」— 事象

**閾値や事象が発言から取れない場合は `不明` と書く。推測で作らない。**
人間が②で埋めるか、`不明` のまま残す（`不明` の signpost を持つ前提は追跡できないので、
②で埋まらなければ `脆弱性` を `中` に落とすのが正しい扱い）。

### 4 — 用語の判定基準

Pass 2 の未知語リストを、既存の用語集と照合して3つに分類する。

| 分類 | 提案 |
|---|---|
| 既存用語の表記崩れ | 既存 TERM の `表記揺れ` への**追記**を提案 |
| 新規用語 | 新規 TERM カードの作成を提案 |
| 一般語・判断不能 | 候補から除外する |

```yaml
  - 種別: 表記揺れの追記
    対象: TERM-012
    追加する表記: [オイデッシー]
    出現回数: 4
    根拠: TERM-012 の読み「オーアイディーシー」に音が近い

  - 種別: 新規用語
    正式: 権限マトリクス
    表記揺れ: []
    定義案: 不明                    # 会議で定義が語られていなければ「不明」
    初出: LOG-20260918-05
    出現回数: 3
```

`定義案` は会議の中で定義が語られていない場合 `不明` とする。推測で定義を書かない。

表記揺れの追記は最も効果が高い（次回の Pass 2 の正規化精度が上がり、引用検証の通過率が上がる）。
出現回数が2回でも、既存用語の崩れと判断できるものは提案してよい。

### 出力形式

```yaml
meeting: MTG-20260918
candidates:
  - 種別: 新規制約
    # （上記の各形式に従う）

  - 種別: 既存制約への紐づけ
    対象: CON-007
    紐づける決定: DEC-020
    根拠: DEC-020 の却下理由「VPN経由だと固定IPが要る」は CON-007 と同内容
    引用: VPN経由だと固定IPが要るんですよね

  - 種別: 新規前提
    # ...

  - 種別: 表記揺れの追記
    # ...

summary:
  新規制約: 1
  既存制約への紐づけ: 1
  新規前提: 1
  表記揺れの追記: 1
  新規用語: 1
```

### 禁止事項

- カードファイルを作成・更新する（承認後に別途行う）
- 4種類以外の提案をする（「この決定は見直すべき」等の意見を書かない）
- `失効条件` `signpost` `定義案` を推測で埋める（`不明` を使う）
- `崩れたら見直す決定` が空の前提を候補に出す
- 固有の事情（工数・スケジュール）を制約として昇格させる
- 1回の会議で **候補を10件以上** 出す（多すぎる場合は根拠の強い順に10件まで）

10件の上限は、人間が承認しきれない量を出さないための制限である。
取りこぼしても次回以降に拾えるため、量より確度を優先する。

---

## 人間の確認（②の後半・5〜10分）

候補リストを上から yes/no で判断する。判断基準は1つだけ。

> **「これは他の決定にも効くか」**

yes なら昇格、no なら捨てる。捨てても次回以降に拾えるため、迷ったら no でよい。

承認したものだけを `constraints/` `assumptions/` `terms/` にカードとして作成する。
`不明` になっているフィールド（`失効条件` `signpost` `定義案`）は、
この場で埋められるなら埋める。埋められなければ `不明` のまま残す。

## 四半期ごとの追加運用（年4回）

Pass 4 とは別に、四半期ごとの定例で**前提の棚卸し**を行う。所要5分。

```
assumptions/ のうち status: 有効 かつ 脆弱性: 高 のものだけをリストアップし、
各前提について signpost が発火していないかを確認する。

崩れていた場合:
  1. status を「崩れた」に変更
  2. 「崩れたら見直す決定」に挙がっている DEC をすべて確認
  3. 見直しが必要な DEC は status を「保留」にして Q を起票
```

これを入れないと、崩れた前提に基づく決定が残り続ける。
制約は破ろうとした時に気づくが、前提は誰にも気づかれずに崩れるため、
定期的な棚卸しだけが検出手段になる。
