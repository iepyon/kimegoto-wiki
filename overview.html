LLM Wiki 業務設計

会議の文字起こしから、ビジネス上のやりとりの意味を構造化したカードを生成する。議事録はそのカードから毎回レンダリングする生成物にすぎない。土台は決定事項・未決定事項・アクションを確実に記録すること。そのうえに、なぜ取り組むのか（取り組まないのか）となぜ代替案を選ばなかったのかを積む。

適用範囲
1チーム / 1PJ定例会議1本から
サイクル
2週に1回半年で13回
人間の作業
25分 / 回年間およそ5.5時間
カード種別
7種フロー4 / ストック3

記録は二層で考える

上の層だけを狙うと、土台のない Wiki になる

土台 — これが本体

決定事項・未決定事項・アクション

会議で何が決まり、何が決まっていないか。どの会社が何をいつまでにやるか。ここが欠けたら上の層は意味を持たない。評価されるのは網羅性で、漏れがないことがそのまま価値になる。

上乗せ — 半年後に効く

なぜ取り組むのか（取り組まないのか）
なぜ代替案を選ばなかったのか

議事録には残らず、文字起こしからしか取れない。取れたときの価値は大きいが、土台の代わりにはならない。取れない回があってもよい層。

この二層は運用上も分かれる。土台はほぼ自動で埋まる（決定・未決・アクションは発言から機械的に拾える）。上乗せは人間が1行書くしかない。だから毎回の25分は、土台の確認ではなく上乗せの記入に使う。

議事録から抽出するのではなく、カードから議事録を作る

設計の向きを反転させる

議事録は「まとめた人が重要だと思ったこと」しか残らない。決定事項は書かれるが、却下された案は議事録化の段階で最初に削られる。「〇〇案は却下」とわざわざ書く議事録はまずない。だから議事録を入力にすると、土台は取れても上乗せ分が原理的に取れない。

入力を生の文字起こしに、順序をカード → 議事録に変えると3つ変わる。

  • 二重管理が消える。カードが唯一の真実で、議事録はその射影。議事録を直してカードが古くなることが起きない。
  • 形式を後から変えられる。社内版・顧客提出版・OpenSpec 入力を、同じカードから別々にレンダリングできる。
  • 粒度が会議単位から論点単位になる。ここが本質。

7種のカード

会議ごとに生成されるフロー層4種と、会議をまたいで育つストック層3種

層型内容同一性
フローLOG 会話ログ論点単位に切り出した逐語の束。他のカードの親であり、すべての引用の照合先毎回新規
フローDEC 決定事項決定・決定の所在（役割）・会議体・範囲（当初合意内/範囲外/判定保留）・却下した代替案とその理由更新される
フローQ 未定事項結論が出ていない論点。確認先と対立当事者を役割で持つ更新される
フローACT アクション会社間の約束。担当は社名、期限つき。唯一「閉じる」型閉じる
ストックCON 制約選択肢を削る環境の性質。種類（property / expectation）で失効条件の要否が変わる1枚が育つ
ストックASM 前提崩れたら決定が覆るもの。逆リンクが本体＋脆弱性＋signpost1枚が育つ
ストックTERM 用語正式名と表記揺れ。溜まると入力品質が上がる唯一の型1枚が育つ

制約の硬度

制約は「誰の事情か」で硬さが違う。顧客側の制約は自社の工夫では変えられないが、自社側の制約には余地がある。硬度は発言者の役割から半自動で決まる。

溶液生ログ・未整理の発言
懸濁自社側の制約・未検証の前提
沈殿顧客側の制約・確定した決定
岩盤契約制約・アーキテクチャ原則

硬度は固定ではない。制約は失効する（顧客がネットワークを更新すれば「VPN固定IPのみ」は消える）ため、失効条件 を必ず持たせる。

役割は「誰が覆せるか」を意味する

話者分離は名前ではなく役割で取る。実名より役割のほうが寿命が長く、匿名なので他チームに実例をそのまま見せられる。そして何より、決定の所在が分かると、その決定を今から変えられるかが引ける。

決定の所在種別半年後の扱い
顧客PM / 発注元交渉可能再提案できる
開発リーダ技術判断前提が変われば覆せる
顧客法務 / 契約契約制約覆せない

アクションだけは社名で持つ。会社間の約束を記録するのがこのカードの役割であり、社内の誰がやるかはタスク管理側の仕事。この線引きで LLM Wiki の責務が決まる。

パイプライン

4つのパスに割る。単一プロンプトにすると逐語引用が崩れる

論点の切り出し・7種への振り分け・同一性判定を一度にやらせると、出力が長くなるほど LLM は引用を要約し始める。引用が壊れると検証機構が全部死ぬので、パスを分ける。

各パスはプロンプトのままでも、スキルとして持たせてもよい。Pass 1 は特に向いている — 入力が文字起こし1本、出力が10行、判断基準が明文化できる（境界シグナル・粒度の原則・種別）。文字起こしを渡すだけで論点の切り出しが返ってくる形にできる。ただしスキルは呼び出しが緩いぶん、「ついでに決定事項も」と逸脱しやすい。Pass 1 の価値は抽出をしないことにあるので、禁止事項（決定・アクションを抽出しない／逐語を引用しない／3〜20件の範囲）を明示的に書いておく必要がある。

逆流を先に作る

溜める動機より引く動機を先に用意しないと定着しない。ACT は2週間で閉じる型で、定例会議で最初に確認されるのが「前回のアクション3件のうち1件が未完了」である。つまり最初から引かれる理由がある。次回アジェンダの自動生成がその入口になる。

引用はプロンプトではなく構造で守る

最大の失敗モードへの対策

文字起こし3万字を渡せば、LLM はもっともらしい却下理由をいくらでも合成できる。しかも一見正しいので人間が通してしまう。「引用は原文のまま」とプロンプトに書いても守られない。だから機械で検証する。

必須フィールドにしない理由必須化は人間にも捏造させる。埋めないと起票できない欄があると、人は埋めるために作り話をする。しかもそれは人間が書いたので「逐語あり」の枠に入り、検証をすり抜ける。

だから なぜ と 却下理由 は任意にし、代わりに3値で状態を持つ。該当なし（そもそも無い）／記録なし（決めたが残っていない = 回収できる負債）／未記入（まだ触っていない）。必須にしなくても、言語化されなかった量はこれで測れる。

MADR 4.0.0 も中核3項目以外をすべて任意にしている（"Feel free to remove any of them"）。同じ結論に別経路で着いている。

ただし、この検証は幻覚しか捕まえない

会議要約の人手エラー注釈では、エラー内訳が欠落 89% / 構造崩れ 57% / 冗長 40% / 非一貫 37% / 幻覚 26%（Kirstein ほか 2024、注釈者間一致 0.81）。欠落は幻覚の3倍以上多い。

引用照合は「言っていないことを言った」を検出するが、「言ったことを落とした」を一切検出しない。ここが設計の穴だったので、プロンプト側に欠落ガードを置いた。

  • 種別が 議論 / 確認 のセグメントでは、DEC / Q / ACT を合わせて最低1件出す
  • 1件も出せない場合は、出せない理由を1行書く
  • 理由が書けないセグメントは review_required を立て、②の確認で人間が見る

自分たちに向けた警告引用一致率を品質指標にしてはいけない。AutoMin 2025 の主催者は、同一システムに対する BART-F1 が 2023年と2025年の計算で負の相関を示したと報告し、ROUGE / BERTScore / BARTScore は「最良システムを他から識別できない」と結論している。引用一致率はグラウンディングの健全性チェックであって、議事録の品質指標ではない。

上乗せ分の取り分

土台（決定・未決・アクションの記録）の上に積まれる2つ

以下は議事録では原理的に取れないもので、この仕組みを組む動機にはなる。ただし土台が埋まっていることが前提で、これ単体では Wiki として使えない。

口に出たが、誰も反応しなかった代替案

会議では「〜という手もあるんですけど」と言われた案が、10秒後に誰の反応もなく流れていく。これは却下だが理由がゼロで、引用できるのは言及だけ。ここを捨てない。

代替案:
  - 案: 自社でID基盤を実装
    却下理由: 記録なし
    引用: 自前で作る手もあるんですけどね
    信頼度: 言及のみ

半年後の「あの案、なぜやらなかったんだっけ」に対して、そもそも検討されずに流れたと答えられる。議事録には100%残らず、文字起こしからしか取れない。

前提の逆リンク

制約は破ろうとしたときに気づくが、前提は誰にも気づかれずに崩れる。「利用者50人だから要らない」と決めたものが、200人になったときに誰も見直さない。前提カードの本体は内容ではなく逆リンクである。

内容: 当面の利用者は50人規模
崩れたら見直す決定: [DEC-014, DEC-019]   # これが本体
検知方法: 月次の利用者数報告

逆リンクが特定できない前提は昇格候補にも出さない。四半期ごとに5分の棚卸しを入れる。これを入れないと前提カードは飾りになる。

絶対に守る3つのルール

どれも破ると静かに壊れる

1 — なぜ と却下理由を LLM に書かせない

書けない場合は 記録なし を入れる。空欄は情報であって、埋めるべき穴ではない。実際の理由は「A社の部長が前にそう言ったから」のように、議事録にも文字起こしにも現れないことが多い。

2 — 迷ったら DEC ではなく Q に落とす

誤起票の害が非対称である。嘘の DEC は半年後まで残り OpenSpec の根拠になるが、余分な Q は次回定例で消える。決定権のない役割の発言だけでは DEC を起票しない。

3 — 承認ワークフローを先に作らない

「リーダのレビュー」を最初から必須にすると、リーダがボトルネックになり3週間で止まる。承認ゼロ・全員書き込み可で回し、矛盾検出が効き始めてから承認を足す。

会議当日の手順

②は会議当日か翌日に固定する。2週間空けると却下理由は思い出せない

  1. Pass 1 を回して粒度を見るLLM人 3分出力は10行。分割しすぎ・粗すぎだけ直す。ここを通してから先に進む。
  2. Pass 2 → Pass 3 → 引用検証LLMLOG カード化、論点ごとの抽出、verify_quotes.py --fix で不一致を降格。待ち時間のみ。
  3. ②-0 範囲: 判定保留 の DEC を見る人 3分受託開発では最優先。他を飛ばしてもここは見る。判定保留のまま放置すると、後で追加請求の根拠を失う。
  4. ②-1 拾い漏れと推測の確認人 4分review_required と欠落ガードの理由を見る。信頼度: 推測 を確認する。最大のエラー源は欠落なのでここを飛ばさない。
  5. ②-2 なぜ を書く人 8分Y-statement の穴埋め。却下理由: 記録なし を埋められるなら埋める。作らない の3値を選ぶ。
  6. ②-3 アクションの担当・期限と状況人 4分担当の社名は自動で入る。空欄が正常な出力（抽出研究でも担当・期限は本文より当てにくい）。前回 ACT の status を更新する。
  7. ②-4 昇格候補の承認人 6分判断基準は1つだけ — 「これは他の決定にも効くか」。ASM は 脆弱性: 高 のものだけ。迷ったら no でよい。次回以降に拾える。
  8. 議事録のレンダリングLLM社内版を生成。リーダのレビュー後、必要なら顧客提出版。未決 Q と未完了 ACT は次回の Pass 0（アジェンダ）に積まれる。

先行研究に照らして直したこと

論証構造・会議理解NLP・実務の記録体系の3方向を調査して差分を取った

同じ問題には50年分の先行研究がある。調べたところ、我々が正しく踏めていた点と、踏み外していた点の両方が出た。

我々が既に踏めていたこと

  • カードが真実源・議事録はレンダリング — Shipman & Marshall (1999) は IBIS 系の失敗要因として「議事録を通常の散文形式に変換しないと外部グループが関与しなかった」と報告している。我々は変換を自動化することで両立させている
  • 迷ったら DEC ではなく Q — 決定検出の精度が 0.43 という実測に対する正しい非対称設計
  • 必須フィールドを作らない — Shipman の premature structure。MADR も中核3項目以外すべて任意
  • Pass 2 → Pass 3 の二段構成 — Kirstein ほか (2025) の FRAME が同型で、幻覚と欠落を両方 3–4/5 → 1/5 に下げている

直した点

直したこと根拠
ASM の 検知方法 → signpost（事象または閾値に限る）。脆弱性 の軸を追加し、高のものだけ追跡Assumption-Based Planning（RAND）の標準用語。「an event or threshold that, if detected, signifies that a vulnerable assumption is being broken」。load-bearing と vulnerable の2軸で絞るのが本来
CON に 種類: property / expectation を追加。property は失効条件が不要KAOS の domain property / expectation の区別。判定テストは「assumptions cannot be enforced by the software-to-be」（van Lamsweerde 2001）
DEC に 範囲: 当初合意内 / 範囲外(追加) / 判定保留。判定保留は自動で Q を起票受託開発の実務。課題ごとに範囲の内外を都度明確にすることが追加請求の根拠になる（裁判例あり）。種別とは直交する軸
顧客提出版にみなし確定の一文（3営業日）。確定日を DEC に書き戻す相手方が確認していない記録は水掛け論を招く。「一定期間内に異議がなければ確定」のルール設定が有効（伊藤雅浩弁護士 2017）
引用は合意・復唱の発話から採る（提案発話は最後）決定発話は Issue / Proposal / Restatement / Agreement に分かれる。提案は言い換えられ撤回される（Fernández ほか 2008）
沈黙由来の却下は 信頼度: 推測 固定（以前は「言及のみ」にしていた）沈黙を却下の根拠に使う手法が文献にない。明示的な合意ですら κ 0.63 / F1 0.39 で最難
欠落ガードを Pass 3 に追加エラー内訳が欠落 89% 対 幻覚 26%。引用検証は幻覚しか捕まえない（Kirstein ほか 2024）
なぜ を Y-statement の穴埋めにする。受容した不利 を追加自由記述は Notes 化して価値を失う（Falessi ほか 2013 の統制実験で13カテゴリ中 Notes だけが一貫して低価値）。Y-statement は Zimmermann
DEC に 確認方法 を追加MADR 4.0.0 の任意項目 Confirmation。DEC / ASM / CON の寿命管理が揃う（下表）
判定ガイドを1枚先に作るADR 実践の最大の障害は記述コストではなく「記録に値するか」の判定。効いた唯一の介入がガイドライン明示（満足度 2.0→2.9）（Ahmeti ほか, ECSA 2024）
なぜ 未記入の DEC は昇格候補になれない＋次回アジェンダに掲示「コスト負担者が受益者と同一でないとき、費用対効果のあるシステムの提供は一層困難になる」（Lee 1997）。書かないことに即時コストを付ける

意識的に受け入れているトレードオフ

Conklin は Dialogue Mapping の価値を成果物ではなく「会議中に生まれる共通理解と、解決策への共有されたコミットメント」に置いている。事後生成の設計はこの価値を構造的に取り逃す。受託開発では顧客との合意形成そのものが成果物なので、小さい犠牲ではない。折衷として「会議中に未決 Q だけは共有画面に出す」程度は検討の余地がある。

3ヶ月後に見る指標

2週に1回だと4回回すのに2ヶ月かかる。焦って別のフックを足さない

始める前にチームに言っておくこと数字は 2006–2008年の統計的分類器（英語, AMI/ICSI）なので現代の LLM は上回る。だが人間の一致率は上限として残る。κ 0.63–0.78 ということは、「決定とは何か」に人間同士で2〜4割の不一致がある。正解率9割は原理的に望めない。

だから「精度が上がれば人間の確認は不要になる」という期待を先に潰しておく。1〜3回目は主役が TERM の起票で、DEC の抽出精度は低く出る。用語集が育つ4回目あたりから逆転する。これを共有しておかないと1回目で止める判断が出る。

日本語の曖昧表現は文献から借りられない調べた範囲で、日本語の業務会議における決定検出・アクション抽出のベンチマークは存在しなかった。CEJC（200時間）は日常会話が対象で業務会議を含まず、日本語の議事録生成の学術文献は議会議事録の1件（定量評価なし）のみ。

「一旦置いといて」「持ち帰ります」「前向きに検討」の扱いは自前で決めるしかない。最初の3〜5会議は、LLM 出力と人間判断の差分を記録するデータ収集フェーズと位置づける。Fernández らの κ 0.63–0.73 が、社内一致率の現実的な目標値の目安になる。

次にやること — ① decision-guide.md の境界例をチームですり合わせる（ここが最大のコスト源）。② role-mapping.yaml の役割ラベル・社名・会議体名を実物に合わせる。話者分離が実際に出すラベル文字列を先に確認すること。1文字違うと Pass 3 が全部「決定権なし」に落ち、DEC が1件も起票されない。③ 次回の定例では Pass 1 だけ回して論点の粒度を見る。
