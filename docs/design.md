# 設計と運用の根拠

使い方の手順は [README](../README.md)。ここには、なぜこの形にしたのか・何を期待してよいか・
3ヶ月後に何を見るかを置く。

---

## 概要

会議の文字起こしから、ビジネス上のやりとりの意味を構造化したカードを生成し、
そのカードから議事録をレンダリングする。カードが唯一の真実で、議事録はその射影。

対象: 1チーム・1プロジェクト。2週に1回の定例会議。
人間の作業: 会議当日25分（年間 約5.5時間）。

---

## 記録は二層

上の層だけを狙うと、土台のない Wiki になる。

| 層 | 内容 | 性質 |
|---|---|---|
| **土台 — これが本体** | 決定事項・未決定事項・アクション | 会議で何が決まり、何が決まっていないか。どの会社が何をいつまでにやるか。**ここが欠けたら上の層は意味を持たない。**評価されるのは網羅性 |
| **上乗せ — 半年後に効く** | なぜ取り組むのか（取り組まないのか）／なぜ代替案を選ばなかったのか | 議事録には残らず、文字起こしからしか取れない。価値は大きいが**土台の代わりにはならない**。取れない回があってもよい |

運用上も分かれる。土台は**ほぼ自動で埋まる**（決定・未決・アクションは発言から機械的に拾える）。上乗せは**人間が1行書くしかない**。だから毎回の25分は、土台の確認ではなく上乗せの記入に使う。

## 全体像

```
音声 ──▶ 文字起こし（話者役割つき）        ← 原本は保管のみ。引用照合には使わない
              │
              │  Pass 1  論点の切り出し        （人間が粒度を確認）
              │  Pass 2  LOG カード化          ← 以降すべての引用の照合先
              ▼
   【フロー層】会議ごとに生成
    LOG 会話ログ ─┬─▶ DEC 決定事項            Pass 3（論点ごとに反復）
                  ├─▶ Q   未定事項  ─┐
                  └─▶ ACT アクション ─┤ 次回アジェンダへ逆流
              │                       │
              │  verify_quotes.py  引用を機械検証・不一致は「推測」に降格
              │  ② 人間の確認 25分     │
              ▼                       │
   【ストック層】会議をまたいで育つ      │      Pass 4（昇格候補 → 人間が承認）
    CON 制約 ／ ASM 前提 ／ TERM 用語
              │                └── TERM の表記揺れが Pass 2 に還流（唯一の自己改善）
              ▼
    OpenSpec（derived_from は自前規約・一方通行）──▶ ソースコード ──▶ デプロイ

    議事録 ◀── カードからレンダリング（社内版／顧客提出版）。保存しない
```

### 設計の3つの軸

1. **議事録は生成物。** カードが元データ。二重管理が起きない。同じ論点が複数回の会議にまたがっても1枚のカードが更新されていく
2. **LLM Wiki → OpenSpec は一方通行。** 逆流させない。実装の都合を知見層に混ぜると、コードの寿命に知見が引きずられる
3. **引用は構造で守る。** 「原文のまま」と指示しても守られない。スクリプトで検証し、一致しないものは自動降格する

### OpenSpec 側の実態（訂正）

OpenSpec は Fission-AI/OpenSpec（MIT, `@fission-ai/openspec`）という実在の単一ツールで、
Thoughtworks Technology Radar Vol.34 (2026-04) で Tools / Assess。
構造は `openspec/{specs, changes, archive}`、change フォルダは
`proposal.md`（why we're doing this, what's changing）/ `specs/` / `design.md` / `tasks.md`。
デルタ見出しは `## ADDED / MODIFIED / REMOVED Requirements` + `### Requirement:` + `#### Scenario:`。

README を確認した結果、**YAML フロントマターもトレーサビリティ欄も存在しない**
（"Plain Markdown — requirements with concrete scenarios, no special syntax to learn"）。

つまり **`derived_from` は OpenSpec の機能ではなく我々の自前規約**である。検証もされない。

- `derived_from: [DEC-014, CON-007]` は `proposal.md` の冒頭行に置く（唯一の理由記述枠がそこ）
- 参考：GitHub Spec Kit の **`[NEEDS CLARIFICATION]` マーカーは我々の Q と同一概念**。
  未解決 Q を流し込めば往復が成立する（OpenSpec にこの受け口はない）
- Spec Kit の `constitution.md` は **CON の `種類: property`**（変わりにくい環境の事実）の
  置き場として最も適合する

### 抽出の判定基準

4つのパスの判定基準は、それぞれのスキルの中にある（`.claude/skills/<名前>/SKILL.md`）。
Pass 4（昇格）は独立したスキルではなく `review` の後半にある（回す順番を守らせるため。下の「会議当日の手順」を参照）。
手順と判定基準を1枚にまとめてあるので、そのパスを回すときはそれだけを読めばよい。

| スキル | 判定基準の中身 |
|---|---|
| `segment` | 論点の定義・境界のシグナル・種別の判定・見出しの付け方 |
| `log-cards` | 逐語の改変規則（削ってよい／言い換え禁止）・検証可能な事実の列挙・未知語の検出 |
| `extract` | 非対称の原則・欠落ガード・役割別の解釈ルール・引用の優先順位・却下パターンの3段階検出・7種への振り分け |
| `review` | 確認②の順序と時間配分・埋まらなかったときの扱い／Pass 4 の昇格の門・制約の判定テスト・前提の検出トリガー・signpost の定義・用語の分類 |
| `minutes` | 社内版と顧客提出版の書式・出せないものの一覧・みなし確定の一文 |

### 道具（Python 3・標準ライブラリのみ）

| コマンド | 内容 |
|---|---|
| `kime lint` | 整合性の機械検査。**error 0 が不変条件**（warning 0 は目指さない） |
| `kime verify-quotes --fix` | 引用の照合と、不一致の「推測」への降格 |
| `kime views` | 横断ビュー・次回アジェンダ・指標の生成 |
| `kime agenda` | 次回アジェンダを標準出力へ |
| `kime review --meeting MTG-...` | 確認②の25分のチェックリスト |
| `kime minutes-input --meeting MTG-... [--edition customer]` | 議事録の材料（顧客版の除外は機械が行う） |
| `kime promote-input --meeting MTG-...` | 昇格候補の材料（**`なぜ` 未記入の決定を落とす**） |
| `kime new <型> --write` | 雛形からカードを起こす（採番つき） |
| `kime update <ID> --set k=v` | 既存カードの書き換え（`--add-derived` / `--log` / `--dry-run`） |
| `kime confirm --meeting MTG-... --sent YYYY-MM-DD` | みなし確定の期限を `確定日` に書き戻す |
| `kime issue --act ACT-NNN` | GitHub Issue の下書き（`--create` で起票） |
| `kime schema --check` | `ontology.yaml` と `schema.md` / 雛形の同期 |

`kime` は `python3 tools/kime.py` のこと。対象の案件は `.env` の
`CURRENT_PROJECT`、または `--root` で指定する。

| 場所 | 内容 |
|---|---|
| `.claude/skills/` | 4パス・確認②（昇格を含む）・議事録／アジェンダ・Issue・lint の7スキル |

## 初回セットアップ（30分）

0. **門を立てる**

   ```
   sh tools/setup.sh
   ```

   `git config core.hooksPath .githooks` を実行し、その場で一度すべての検査を通す。
   **これを飛ばすと `.githooks/pre-commit` は動かない。** clone しただけでは
   git はこのディレクトリを見に行かないため、「門がある」と思ったまま門の無い
   状態で作業することになる。

   `--no-verify` での迂回は塞げないので、同じ門を CI
   （`.github/workflows/checks.yml`）がもう一度通す。迂回したこと自体は
   止められないが、後から気づけるようにしてある。

1. **`decision-guide.md` を読んで、チームで境界例をすり合わせる**
   - Ahmeti ほか (ECSA 2024) のアクションリサーチで、最大の障害は記述コストではなく
     「これは記録に値するか」の**判定**だった。ADR 自体は "really easy to write" と評価されている
   - そして効いた唯一の介入が**ガイドラインの明示**（満足度 2.0→2.9 / 2.5→3.1）
   - だからここを飛ばさない

2. **`role-mapping.yaml` を埋める**
   - 話者分離が出力する役割ラベルを key にする（表記を合わせる）
   - 顧客社名と、契約上の**会議体名**を入れる
   - 各役割の `決定権` と `決定の種別` を決める ← ここが Pass 3 の精度を決める

3. **案件のディレクトリを作る**

   ```
   cp -r templates/project projects/<案件名>
   sh tools/setup.sh <案件名>          # .env に書き、門を通す
   ```

   `role-mapping.yaml` は案件ディレクトリの中に置く。

4. **既存の用語集を TERM カードに移す**
   - `正式` だけ入れれば足りる。`表記揺れ` は回しながら育てる

5. **対象会議を1本決める**
   - 自分が出席する定例1本だけ。増やさない

## 会議当日の手順

### ① 抽出（LLM・30分程度／待ち時間）

```
Pass 1  →  segments.yaml を人間が確認（粒度の調整）← ここだけ人が見る
Pass 2  →  LOG カード生成 + 未知語リスト
Pass 3  →  論点ごとに反復実行（DEC / Q / ACT）
python3 tools/kime.py scope-questions --meeting MTG-...  ← 範囲の問いを定型で起票
python3 tools/kime.py verify-quotes --fix  ← 引用を検証、不一致は「推測」に降格
python3 tools/kime.py lint                 ← error 0 を確認
```

**Pass 4 は①では回さない。** `kime promote-input` は理由がどこにも記録されていない
決定を材料から落とす。①の時点では `なぜ` が必ず未記入なので、材料が痩せる。
②の 2-2 で `なぜ` を書いたあと、2-4 の直前に回す（下表）。順番を守らせるために、
Pass 4 は独立したスキルではなく `/review` の中に置いてある。

Claude Code では `/segment` `/log-cards` `/extract` のスキルが
それぞれのパスに対応する。Pass 4（昇格）は `/review` が②の中で続けて回す。

### ② 確認（人間・25分／**会議当日か翌日に固定**）

2週間空けると却下理由は思い出せない。ここは当日中に済ませる。

| | 内容 | 目安 |
|---|---|---|
| 2-0 | **`範囲: 判定保留` の DEC を見る。** 受託開発では最優先。他を飛ばしてもここは見る | 3分 |
| 2-1 | `review_required` と欠落ガードの理由を確認（拾い漏れがないか）／`信頼度: 推測` を確認 | 4分 |
| 2-2 | DEC の `なぜ` を1行書く（Y-statement の穴埋め）／`却下理由: 記録なし` を埋められるなら埋める／`作らない` の3値を選ぶ | 8分 |
| 2-3 | ACT の担当・期限を入れる（空欄が正常な出力）／前回 ACT の status を更新 | 4分 |
| 2-4 | **ここで Pass 4 を回し**（`/review` が続けて進行する）、出た昇格候補を yes/no で承認（ASM は `脆弱性: 高` のものだけ） | 6分 |

`python3 tools/kime.py review --meeting MTG-YYYYMMDD` が、この順序で
**該当するカードだけ**を並べて出す（0件の節は「0件」とだけ出る）。
Claude Code では `/review` スキルが進行する。

**`なぜ` を書かないことのコスト**（必須フィールドを作らずに記入を促す仕掛け）

- `なぜ` 未記入の DEC は**次回アジェンダ冒頭に自動掲示される**
- `なぜ` も `代替案[].却下理由` も無い DEC は **CON / ASM への昇格候補になれない**
  （その制約が将来の議論で効かない）。却下理由が逐語で取れている決定は通る —
  CON の中身は捨てた案の理由であって、採った案の理由ではないため

根拠：Lee (1997) は「コスト負担者が受益者と同一でないとき、費用対効果のあるシステムを
提供することは一層困難になる」とし、処方の1つにインセンティブを挙げている。
上乗せ層は「書く人が得をしない」構造なので、書かないことに即時コストを付ける。

### ③ 議事録（LLM・5分）

`python3 tools/kime.py minutes-input --meeting MTG-YYYYMMDD` で材料を組み立て、
`/minutes` スキルで社内版を生成する。リーダのレビュー後、必要なら
`--edition customer` で顧客提出版を生成して PDF 化。

**顧客提出版で出せない情報は CLI が機械的に落とす**（`ontology.yaml` の
`editions.customer` に宣言がある）。漏れたら契約上の事故になるので、
LLM の遵守に賭けない。LLM の仕事は残った情報の文章化だけ。

### ④ 次回アジェンダ（LLM・自動）

- `status: 未決` の Q すべて
- `完了` `取り下げ` 以外の ACT すべて
- 四半期に1回: `status: 有効` かつ `脆弱性: 高` の ASM だけ棚卸し（5分）

`python3 tools/kime.py agenda` が出す。Stop フックがターンの終わりに
`views/agenda-next.md` を作り直すので、人が忘れても勝手に出てくる。

**④ が「Wiki を使う動機」になる。** 溜める動機より引く動機を先に作るのが定着の条件。

## 絶対に守る3つのルール

### 1. `なぜ` と却下理由を LLM に書かせない

文字起こし3万字を渡せば、LLM はもっともらしい理由をいくらでも合成する。
しかも一見正しいので人間が通す。**これがこの仕組みの最大の失敗モード。**

書けない場合は `記録なし` を入れる。空欄は情報であり、埋めるべき穴ではない。

### 2. 迷ったら DEC ではなく Q に落とす

誤起票の害が非対称。嘘の DEC は半年後まで残り OpenSpec の根拠になるが、
余分な Q は次回定例で消える。判断を DEC 側に寄せないこと。

決定権のない役割の発言だけでは DEC を起票しない。

### 3. 承認ワークフローを先に作らない

「リーダのレビュー」を最初から必須にすると、リーダがボトルネックになり3週間で止まる。
最初は承認ゼロ・全員書き込み可で回し、矛盾検出が効き始めてから承認を足す。

## 上乗せ分の取り分

以下は議事録では原理的に取れないもので、この仕組みを組む動機になる。
ただし**土台（決定・未決・アクション）が埋まっていることが前提**で、これ単体では Wiki として使えない。

**「口に出たが誰も反応しなかった代替案」が残る。**

```yaml
代替案:
  - 案: 自社でID基盤を実装
    却下理由: 記録なし
    引用: 自前で作る手もあるんですけどね
    信頼度: 推測          # 沈黙由来の却下は 推測 固定
```

議事録には100%残らない。文字起こしからしか取れない。
半年後の「あの案、なぜやらなかったんだっけ」に対して
**「そもそも検討されずに流れた」**と答えられるのは、ここだけ。

もう一つは**前提の逆リンク**。制約は破ろうとした時に気づくが、前提は誰にも気づかれずに崩れる。
`崩れたら見直す決定: [DEC-014, DEC-019]` があれば、
利用者が50人から200人になった時に、どの決定を見直すべきかが引ける。

## 既知の難所

| 難所 | 対処 |
|---|---|
| **論点の粒度** | 3回回さないと適正が出ない。Pass 1 の出力が10行なので、そこで安く調整する。最初は粗めに切り、分割したくなったら分ける |
| **カードの同一性判定** | 「これは Q-031 の続き」の判定は、用語集が育つまで精度が出ない。最初の3回は人間が指定する前提で組む |
| **1〜3回目の結果は悪い** | 主役は TERM の起票で、DEC の抽出精度は低く出る。4回目あたりから逆転する。**始める前にチームに言っておく**（1回目で止める判断を防ぐ） |
| **検証サイクルが遅い** | 2週に1回だと4回回すのに2ヶ月。フックが正しいかの結論が出るのは3ヶ月後。焦って別のフックを足さない |
| **② を飛ばす誘惑** | 飛ばすと捏造されたWikiができる。25分が払えない週は、Pass 3 まで止めて翌週まとめてやる方がまだよい |
| **日本語の曖昧表現は文献から借りられない** | 「一旦置いといて」「持ち帰ります」「前向きに検討」の扱いは、日本語の業務会議ベンチマークが存在しないため自前で決めるしかない。最初の3〜5会議はデータ収集フェーズと位置づける |

## 期待値の較正（実測値）

「精度が上がれば人間の確認は不要になる」という期待を最初に潰しておく。

| 項目 | 実測 | 出典 |
|---|---|---|
| 決定対話行為の**人間の注釈一致** | κ 0.63–0.73 | Fernández ほか 2008 |
| アクション項目の**人間の一致** | κ 0.435–0.78 | Purver 2007 / Morgan 2006 |
| 決定対話行為の出現頻度 | 全発話の **4.3%** | Fernández ほか 2008 |
| 決定サブ対話の**位置**検出 | F1 0.58（精度 0.43 / 再現 0.88） | Fernández ほか 2008 |
| 決定の**構成要素**の同定 | F1 0.16–0.39 | Fernández ほか 2008 |
| アクション項目検出 | F 0.32 | Morgan ほか 2006 |
| トピック分割 | Pk 0.33–0.41（**境界の約3割が誤り**） | Solbiati ほか |
| 会議要約の事実不整合（グラウンディングなし） | サンプルの **74%** | QMSum, Zhong 2021 |
| 会議要約のエラー内訳 | **欠落 89% / 幻覚 26%** | Kirstein ほか 2024 |

数字は 2006–2008 年の統計的分類器（英語, AMI/ICSI）なので現代の LLM は上回る。
だが **人間の一致率は上限として残る**。κ 0.63–0.78 ということは、
「決定とは何か」に人間同士で2〜4割の不一致がある。**正解率9割は原理的に望めない。**

そして**最大のエラー源は幻覚ではなく欠落**（89% 対 26%）。
引用検証スクリプトは幻覚しか捕まえないので、Pass 3 側に欠落ガードを置いている。

詳細と出典は `research-notes.md`。

## 判定基準（3ヶ月後に見るもの）

| 層 | 指標 | 読み方 |
|---|---|---|
| 土台 | **決定・未決・アクションの網羅性** | **まずここ。** 1回分をランダムに選び、人が議事録を読んで拾った決定・未決と突き合わせる。漏れがあるなら他の指標を見る意味がない |
| 土台 | 次回アジェンダが実際に使われた回数 | 未決 Q と未完了 ACT が定例の冒頭で読まれているか。引かれない記録は死んでいる |
| 上乗せ | **OpenSpec が `derived_from` で引いた DEC の数** | 上乗せ分が使われているかの本命。0 に近いなら、溜めた理由や制約が参照されていない |
| 上乗せ | 矛盾検出が発火した回数 | 過去の決定と逆の決定を検出できたか。1回でも出れば元は取れている |
| 上乗せ | `却下理由: 記録なし` の比率 | 高いままなら、会議で代替案が言語化されていない。Wiki の問題ではなく意思決定の仕方の問題 |
| 上乗せ | ASM の棚卸しで「崩れた」判定が出た数 | 前提の逆リンクが機能しているか |
| 共通 | `信頼度: 推測` の件数 | 抽出プロンプトか話者分離の精度の問題 |
| 共通 | `review_required` が立ったセグメント数 | 欠落ガードの発火。多いなら Pass 3 のプロンプトか粒度の問題 |

**引用一致率を品質指標にしないこと。** AutoMin 2025 の主催者は、同一システムに対する
BART-F1 が 2023 年と 2025 年の計算で**負の相関**を示したと報告し、ROUGE / BERTScore / BARTScore は
「最良システムを他から識別できない」と結論している。自動指標を品質指標に昇格させると同じ罠に落ちる。
引用一致率はグラウンディングの健全性チェックであって、議事録の品質指標ではない。

土台が埋まっていて上乗せが薄いだけなら、フックは正しく、意思決定の言語化が薄いということ。
それは Wiki の外の問題で、フックを差し替えても直らない。

土台そのものが埋まらないなら、2週に1回の定例がフックとして細すぎる。
その場合は「見積り・優先度付けの瞬間」か「顧客要望への回答（メール）」を足す。

## 意識的に受け入れているトレードオフ

**会議中に生まれる共通理解を、この設計は構造的に取り逃す。**

Conklin は Dialogue Mapping の価値を成果物ではなく「会議中に生まれる共通理解と、
解決策への共有されたコミットメント」に置いている。事後生成の設計はこの価値を取れない。

受託開発では**顧客との合意形成そのものが成果物**なので、小さい犠牲ではない。
折衷として「会議中に未決 Q だけは共有画面に出す」程度は検討の余地がある。

採らなかった他のアプローチ（IBIS のリアルタイム図式化、QOC/DRL の評価マトリクス、
Toulmin モデル、argument mining の自動リンク、RAID ログ、KAOS の形式的 obstacle analysis、
ADR のピアレビュー前置）とその理由は `research-notes.md` に記録してある。
