# 設計と運用の根拠

使い方の手順は [README](../README.md)、各パスの手順と判定基準は `.claude/skills/`、
守るルールは `CLAUDE.md`。ここには、なぜこの形にしたのか・何を期待してよいか・
3ヶ月後に何を見るかだけを置く。

---

## 概要

会議の文字起こしから、ビジネス上のやりとりの意味を構造化したカードを生成し、
そのカードから議事録をレンダリングする。カードが唯一の真実で、議事録はその射影。

対象: 1チーム・1プロジェクト。2週に1回の定例会議。
人間の作業: 会議当日25分（年間 約5.5時間）。

---

## 記録は二層

上の層だけを狙うと、土台のない Wiki になる。

| 層 | 内容 | 性質 |
|---|---|---|
| **土台 — これが本体** | 決定事項・未決定事項・アクション | 会議で何が決まり、何が決まっていないか。どの会社が何をいつまでにやるか。**ここが欠けたら上の層は意味を持たない。**評価されるのは網羅性 |
| **上乗せ — 半年後に効く** | なぜ取り組むのか（取り組まないのか）／なぜ代替案を選ばなかったのか | 議事録には残らず、文字起こしからしか取れない。価値は大きいが**土台の代わりにはならない**。取れない回があってもよい |

運用上も分かれる。土台は**ほぼ自動で埋まる**（決定・未決・アクションは発言から機械的に拾える）。上乗せは**人間が1行書くしかない**。だから毎回の25分は、土台の確認ではなく上乗せの記入に使う。

## 全体像

```
音声 ──▶ 文字起こし（話者役割つき）        ← 原本は保管のみ。引用照合には使わない
              │
              │  Pass 1  論点の切り出し        （人間が粒度を確認）
              │  Pass 2  LOG カード化          ← 以降すべての引用の照合先
              ▼
   【フロー層】会議ごとに生成
    LOG 会話ログ ─┬─▶ DEC 決定事項            Pass 3（論点ごとに反復）
                  ├─▶ Q   未定事項  ─┐
                  └─▶ ACT アクション ─┤ 次回アジェンダへ逆流
              │                       │
              │  kime verify-quotes  引用を機械検証・不一致は「推測」に降格
              │  ② 人間の確認 25分     │
              ▼                       │
   【ストック層】会議をまたいで育つ      │      Pass 4（昇格候補 → 人間が承認）
    CON 制約 ／ ASM 前提 ／ TERM 用語
              │                └── TERM の表記揺れが Pass 2 に還流（唯一の自己改善）
              ▼
    OpenSpec（derived_from は自前規約・一方通行）──▶ ソースコード ──▶ デプロイ

    議事録 ◀── カードからレンダリング（社内版／顧客提出版）。保存しない
```

### 設計の3つの軸

1. **議事録は生成物。** カードが元データ。二重管理が起きない。同じ論点が複数回の会議にまたがっても1枚のカードが更新されていく
2. **LLM Wiki → OpenSpec は一方通行。** 逆流させない。実装の都合を知見層に混ぜると、コードの寿命に知見が引きずられる
3. **引用は構造で守る。** 「原文のまま」と指示しても守られない。スクリプトで検証し、一致しないものは自動降格する

次回アジェンダ（カードの射影）が、この仕組みを使う動機になる。溜める動機より引く動機を先に作るのが定着の条件。

OpenSpec との連携の規約（`derived_from` は OpenSpec の機能ではなく自前の規約）は
[`openspec-bridge.md`](openspec-bridge.md)。

## 上乗せ分の取り分

以下は議事録では原理的に取れないもので、この仕組みを組む動機になる。
ただし**土台（決定・未決・アクション）が埋まっていることが前提**で、これ単体では Wiki として使えない。

**「口に出たが誰も反応しなかった代替案」が残る。**

```yaml
代替案:
  - 案: 自社でID基盤を実装
    却下理由: 記録なし
    引用: 自前で作る手もあるんですけどね
    信頼度: 推測          # 沈黙由来の却下は 推測 固定
```

議事録には100%残らない。文字起こしからしか取れない。
半年後の「あの案、なぜやらなかったんだっけ」に対して
**「そもそも検討されずに流れた」**と答えられるのは、ここだけ。

もう一つは**前提の逆リンク**。制約は破ろうとした時に気づくが、前提は誰にも気づかれずに崩れる。
`崩れたら見直す決定: [DEC-014, DEC-019]` があれば、
利用者が50人から200人になった時に、どの決定を見直すべきかが引ける。

## 既知の難所

| 難所 | 対処 |
|---|---|
| **論点の粒度** | 3回回さないと適正が出ない。Pass 1 の出力が10行なので、そこで安く調整する。最初は粗めに切り、分割したくなったら分ける |
| **カードの同一性判定** | 「これは Q-031 の続き」の判定は、用語集が育つまで精度が出ない。最初の3回は人間が指定する前提で組む |
| **1〜3回目の結果は悪い** | 主役は TERM の起票で、DEC の抽出精度は低く出る。4回目あたりから逆転する。**始める前にチームに言っておく**（1回目で止める判断を防ぐ） |
| **検証サイクルが遅い** | 2週に1回だと4回回すのに2ヶ月。フックが正しいかの結論が出るのは3ヶ月後。焦って別のフックを足さない |
| **② を飛ばす誘惑** | 飛ばすと捏造されたWikiができる。25分が払えない週は、Pass 3 まで止めて翌週まとめてやる方がまだよい |
| **日本語の曖昧表現は文献から借りられない** | 「一旦置いといて」「持ち帰ります」「前向きに検討」の扱いは、日本語の業務会議ベンチマークが存在しないため自前で決めるしかない。最初の3〜5会議はデータ収集フェーズと位置づける |

## 期待値の較正（実測値）

「精度が上がれば人間の確認は不要になる」という期待を最初に潰しておく。

| 項目 | 実測 | 出典 |
|---|---|---|
| 決定対話行為の**人間の注釈一致** | κ 0.63–0.73 | Fernández ほか 2008 |
| アクション項目の**人間の一致** | κ 0.435–0.78 | Purver 2007 / Morgan 2006 |
| 決定対話行為の出現頻度 | 全発話の **4.3%** | Fernández ほか 2008 |
| 決定サブ対話の**位置**検出 | F1 0.58（精度 0.43 / 再現 0.88） | Fernández ほか 2008 |
| 決定の**構成要素**の同定 | F1 0.16–0.39 | Fernández ほか 2008 |
| アクション項目検出 | F 0.32 | Morgan ほか 2006 |
| トピック分割 | Pk 0.33–0.41（**境界の約3割が誤り**） | Solbiati ほか |
| 会議要約の事実不整合（グラウンディングなし） | サンプルの **74%** | QMSum, Zhong 2021 |
| 会議要約のエラー内訳 | **欠落 89% / 幻覚 26%** | Kirstein ほか 2024 |

数字は 2006–2008 年の統計的分類器（英語, AMI/ICSI）なので現代の LLM は上回る。
だが **人間の一致率は上限として残る**。κ 0.63–0.78 ということは、
「決定とは何か」に人間同士で2〜4割の不一致がある。**正解率9割は原理的に望めない。**

そして**最大のエラー源は幻覚ではなく欠落**（89% 対 26%）。
引用検証スクリプトは幻覚しか捕まえないので、Pass 3 側に欠落ガードを置いている。

## 判定基準（3ヶ月後に見るもの）

| 層 | 指標 | 読み方 |
|---|---|---|
| 土台 | **決定・未決・アクションの網羅性** | **まずここ。** 1回分をランダムに選び、人が議事録を読んで拾った決定・未決と突き合わせる。漏れがあるなら他の指標を見る意味がない |
| 土台 | 次回アジェンダが実際に使われた回数 | 未決 Q と未完了 ACT が定例の冒頭で読まれているか。引かれない記録は死んでいる |
| 上乗せ | **OpenSpec が `derived_from` で引いた DEC の数** | 上乗せ分が使われているかの本命。0 に近いなら、溜めた理由や制約が参照されていない |
| 上乗せ | 矛盾検出が発火した回数 | 過去の決定と逆の決定を検出できたか。1回でも出れば元は取れている |
| 上乗せ | `却下理由: 記録なし` の比率 | 高いままなら、会議で代替案が言語化されていない。Wiki の問題ではなく意思決定の仕方の問題 |
| 上乗せ | ASM の棚卸しで「崩れた」判定が出た数 | 前提の逆リンクが機能しているか |
| 共通 | `信頼度: 推測` の件数 | 抽出プロンプトか話者分離の精度の問題 |
| 共通 | `review_required` が立ったセグメント数 | 欠落ガードの発火。多いなら Pass 3 のプロンプトか粒度の問題 |

**引用一致率を品質指標にしないこと。** AutoMin 2025 の主催者は、同一システムに対する
BART-F1 が 2023 年と 2025 年の計算で**負の相関**を示したと報告し、ROUGE / BERTScore / BARTScore は
「最良システムを他から識別できない」と結論している。自動指標を品質指標に昇格させると同じ罠に落ちる。
引用一致率はグラウンディングの健全性チェックであって、議事録の品質指標ではない。

土台が埋まっていて上乗せが薄いだけなら、フックは正しく、意思決定の言語化が薄いということ。
それは Wiki の外の問題で、フックを差し替えても直らない。

土台そのものが埋まらないなら、2週に1回の定例がフックとして細すぎる。
その場合は「見積り・優先度付けの瞬間」か「顧客要望への回答（メール）」を足す。

## 意識的に受け入れているトレードオフ

**会議中に生まれる共通理解を、この設計は構造的に取り逃す。**

Conklin は Dialogue Mapping の価値を成果物ではなく「会議中に生まれる共通理解と、
解決策への共有されたコミットメント」に置いている。事後生成の設計はこの価値を取れない。

受託開発では**顧客との合意形成そのものが成果物**なので、小さい犠牲ではない。
折衷として「会議中に未決 Q だけは共有画面に出す」程度は検討の余地がある。

採らなかった他のアプローチ（IBIS のリアルタイム図式化、QOC/DRL の評価マトリクス、
Toulmin モデル、argument mining の自動リンク、RAID ログ、KAOS の形式的 obstacle analysis、
ADR のピアレビュー前置）の検討と出典は、削除した `research-notes.md` に残っている
（`git show 32db73b:research-notes.md`）。
