## 問題（実際に踏んだものだけ）

### 1. 昇格の門と作業順序が噛み合わず、ストック層が1枚も作れない ★最大（順序は修正済み／門は未修正）

5回まわして **CON 0 / ASM 0 / TERM 0**。原因は仕組みの順序。

- `README.md` の手順は ①Pass 1〜4 →②確認25分（2-2 で `なぜ` を書き、2-4 で昇格を承認）
- しかし `giji promote-input` は **`なぜ` が未記入の DEC を材料から落とす**
- ①の時点では `なぜ` は必ず未記入。したがって Pass 4 の材料は**常に空**になる

5回分の `promote-input` はすべて「決定と却下理由（昇格の門を通ったもの）: （なし）」を返した。
結果、`DEC-005` の却下理由「社外にデータを出すのは規程上できません」
（顧客法務 / property × 契約 ＝ **岩盤**）という最も硬い制約候補が、1回も候補に出ていない。

**さらに筋が通っていない点。** 門の根拠は「理由が記録されていない制約は将来の議論で効かない」だが、
CON の中身は DEC の `なぜ`（採った案の理由）ではなく `代替案[].却下理由`（捨てた案の理由）である。
`decision-guide.md` 自身が「`受容した不利` は `代替案[].却下理由` とは別物」と書いている。
**別物で門を作っている。**

改善案:

- (a) ②の順序を `2-2（なぜ）→ Pass 4 → 2-4（承認）` に変える。
  `README.md` の①②の図と `.claude/skills/review/SKILL.md` の 2-4 に「Pass 4 はここで回す」と書く
- (b) 門の条件を `なぜ` から **`代替案[].却下理由` が `記録なし` 以外**に変える
  （`tools/bundle.py` の `main_promote` 側）
- (c) ASM は `崩れたら見直す決定` が特定できていれば通す（`なぜ` と独立の門にする）

推奨は **(a) と (b) の併用**。(a) だけだと、なぜが書けなかった回に制約が拾えないまま流れる。

### 2. `範囲: 判定保留` の自動 Q 起票が、未決の問いを水増しする

DEC 15枚中 **10枚**が `判定保留`。規約どおり全部に Q を起票した結果、
Q 17枚中 **9枚**が「〈決定〉は当初合意範囲内か」になった。
次回アジェンダの未決 Q 11件のうち 9件がこれで、**アジェンダが範囲判定で埋まる**。

しかも `種別: 技術判断` の決定にも一律で起票される。
「索引の更新は夜間バッチで行うは当初合意範囲内か」（Q-010）を顧客PMに聞く価値は薄い。

改善案:

- 自動 Q 起票を `種別: 交渉可能` / `契約制約` に限る。技術判断が範囲交渉の対象になるのは
  工数が増えるときだけで、その場合は発話に「見積に入っていない」が現れる
- あるいは会議ごとに1枚へまとめる（「MTG-YYYYMMDD の範囲判定（対象: DEC-009, DEC-015）」）
- 正本は `.claude/skills/extract/SKILL.md` の「`範囲` の判定」節

### 3. 顧客提出版で ACT の `担当` が「不明」になる ★バグ（**修正済み**）

```
python3 tools/giji.py minutes-input --root projects/demo-kb \
    --meeting MTG-20260911 --edition customer
```

> ### ベクタDBの監視とバックアップの手順書を提供する
> - 担当: 不明          ← カードには `担当: B社` と入っている

`tools/bundle.py:174` が `担当` を `company_of()` に通す。`担当` は
**すでに社名**（`schema.md` ACT 節「担当は社名で持つ」）なので、
`Wiki.role("B社")` が `unknown_role_default` にフォールバックし、`社名: 不明` が返る。

**顧客に出す文書から自社名が消える。** 契約上の約束の主体が落ちるので実害がある。

改善案: `company_of()` で、値が `Wiki.companies`（`tools/cards.py:328` に既にある）に
含まれるならそのまま返す。`tests/test_bundle.py` に「担当が社名のまま残る」を1本足す。

### 4. 範囲判定の Q がそのまま顧客提出版に出る

顧客版の「未決事項」に
「全社展開に向けた構成見直しを含めないは当初合意範囲内か」が出た。
**自社が当初合意の範囲を測りかねていることを、対外文書で開示する**ことになる。

問題2と同根。改善案は Q に由来を持たせて `ontology.yaml` の
`editions.customer.exclude` で落とすこと（例: Q に `種別: 範囲判定` を足す）。
問題2を先に直せば件数自体が減るので、そちらが先。

- `ontology.yaml` に該当フィールドが無い（LOG は不変層なので後から書き足せない）
- 書き出すファイルの指定も無い

今回 `log-barren` が3件（LOG-20260717-01 / -04 / LOG-20260731-06）出たが、
**理由を書く場所が無いので書いていない**。ガードが宣言だけで閉じていない。

`log-barren` はそこに理由がある LOG を warning から外す。

### 6. `覆された` 決定に `scope-pending-q` が誤発火（**修正済み**）

DEC-005（`status: 覆された` / `superseded_by: DEC-011`）に対して
「`範囲: 判定保留` だが、同じ論点に未決の Q が無い」が出る。
対応する Q-005 は決定が覆ったので `取り下げ` にしてあり、これが正しい状態。

改善案: `tools/gijilint.py` の `check_scope_pending_q` で `status: 覆された` を除外する。

### 7. カードの更新に道具が無い

会議をまたぐ更新は全部手編集だった。5回分で **22箇所**:

- Q の `status: 解決` + `resolved_by`（6件）
- ACT の `status` と `更新履歴`（10件）
- DEC の `status: 覆された` + `superseded_by`（1件）
- 既存カードの `derived_from` への LOG 追記（多数）

`giji new` は新規作成だけで、`--write` は既存ファイルがあれば拒否する（`tools/new_cmd.py:93`）。
**カードと会議が多対多**という設計の中心が、いちばん手作業に晒されている。

改善案:

```
giji update Q-002 --set status=解決 --set resolved_by=DEC-012 \
                  --add-derived LOG-20260828-04 --last-mention 2026-08-28
giji update ACT-011 --set status=遅延 --log '2026-09-11: 未提出。来週中に提示と回答'
```

frontmatter を行単位で置き換える実装は `tools/quotes.py` の `fix_card` が既に持っている。
同じ技法で書ける。

### 8. `報告` セグメントの DEC スキップが、decision-guide の境界例と衝突

`decision-guide.md` の境界例:「そのあたりは任せます（顧客PM）→ **DEC**（判断の委任そのものが決定）」。

今回 LOG-20260717-05 に同じ発話があるが、この論点は `種別: 報告`（技術方式の説明）なので、
`extract` スキルの手順2で **DEC 抽出をスキップ**する。結果、この委任は記録に残っていない。

Pass 1 の `種別` 判定が Pass 3 の再現率の上限になる構造で、
README の実測表は「トピック分割は境界の約3割が誤る」と書いている。**上限が3割ずれる。**

改善案: `報告` / `雑談` でも「決定権のある役割による結論の表明」だけは **Q として拾う**
（DEC にはしない）。「迷ったら DEC ではなく Q」の非対称原則と整合し、欠落だけを減らせる。

### 9. 未登録の役割から生えたアクションは担当が埋まらない

### 10. `信頼度: 推測` の指標が代替案を数えない（**修正済み**）

### 11. `確定日` を書き戻す道具が無い

`dec-unconfirmed` が12件。顧客提出版の末尾には

**`確定日` を書き戻すコマンドが無い**。人間が15枚に手で日付を入れることになる。

改善案: `giji confirm --meeting MTG-YYYYMMDD --sent 2026-09-12` で、
その会議の決定の `確定日` に3営業日後を書く。

### 12. `transcript.md` の形式が未規定

改善案: `.fixture` と別に `.wip` を見て除外する。あるいは `stop_lint` が

## この作業中に生じた決定（暗黙にしない）

- `transcript.md` の書式を上記のとおり決め打ちした（問題12）
- **Pass 1 の人間確認ゲートを5回分まとめて飛ばした。** スキルは
  「人間に粒度の確認を求めてそこで止まる」と指示しているが、5会議を一括で処理した。
  粒度確認は運用の核なのでスキルを緩めるべきではない。代わりに
  「過去回の `segments.yaml` があるなら、前回の粒度との差分だけを見せる」手順を足すと
  2回目以降が安くなる
- `なぜ` / `代替案[].却下理由` / ACT の `担当`・`期限` / 昇格の承認は**1つも埋めていない**。
  規約どおり人間の仕事として残してある（`CLAUDE.md` ルール1・スキル共通規約4）
- `role-mapping.yaml` の `meta` に `会議体: 定例WG` を足した。
  `templates/project/README.md` は「会議体名を埋める」と指示するのに、
  雛形にその欄が無い（小さな不整合）
