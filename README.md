# kimegoto — 決め事を記録するキット

会議の文字起こしから、**決定事項（DEC）・未決事項（Q）・アクション（ACT）** をカードとして
抜き出し、そのカードから議事録と次回アジェンダを作る。
**カードが唯一の真実で、議事録はその射影。**

名前は「決め事（きめごと）」から。CLI は `kime`（`python3 tools/kime.py`）。

対象: 1チーム・1プロジェクト。2週に1回の定例会議。
人間の作業: 会議当日の確認 25分。

この README は、**Claude Code に話しかけてスキルを動かす**チュートリアル。
コマンドを覚える必要はない。なぜこの形にしたのか、何を期待してよいか、
3ヶ月後に何を見るかは [`docs/design.md`](docs/design.md) にある。

---

## 1サイクルの流れ

![1サイクルの流れ: ① アジェンダ → 会議 → ② 取り込む → ③ 抽出する → ④ 人が確認する → ⑤ 議事録。開いた議題が次回の ① に戻る](docs/images/cycle.svg)

利用者が覚える頼み方は**4つ**。会議 ID や段の順番は道具が知っている。

| | 頼み方 | 動くスキル | 人がやること |
|---|---|---|---|
| ① 会議の前 | 「次回のアジェンダを出して」「次の会議でこれを決めたい」 | `/agenda` | 読む。決めたいことを言う |
| ②③ 会議の後 | transcript.md を置いて「会議を取り込んで」 | `/ingest`（Pass 1〜3 を一続きで） | **論点の粒度を一度確認する**だけ |
| ④ 確認 | 「確認を始めて」 | `/review`（25分） | `なぜ`・担当・期限・スコープ・議題の締めを**判定**する |
| ⑤ 出力 | 「議事録を出して」 | `/minutes` | 読んで送る |

迷ったら「**今どこ？**」と聞く。いまの会議・どこまで済んだか・次にやることが1枚で出る
（中身は `kime status`）。途中で切れても「続けて」で再開できる。

スキルは `/agenda` のようにスラッシュで呼んでも、上の表の言い方で頼んでもよい。
Claude が頼み方からスキルを選ぶ。

---

## チュートリアルの進め方

このリポジトリを Claude Code で開いて進める（必要なのは `python3` と `git` だけ）。

| | やること | 時間 |
|---|---|---|
| [A](#a-5分で眺める記録済みのデモ) | 記録済みのデモで、出来上がりを眺める | 5分 |
| [B](#b-1サイクルを回す練習用の案件) | 練習用の案件を作り、架空の会議を1回分、アジェンダから議事録まで通す | 40分 |
| [C](#c-2回目の会議持ち越しと更新) | 2回目の会議を取り込み、持ち越しとカードの更新を見る | 20分 |
| [D](#d-答え合わせと片付け) | 同じ会議を記録済みのデモと見比べ、練習用の案件を消す | 5分 |

B と C の題材は、同梱のデモ案件 `projects/demo-kintai`（勤怠・経費システム改修、架空）の
文字起こし。デモには同じ会議の記録が入っているので、D で答え合わせができる。

## A. 5分で眺める：記録済みのデモ

まず、回し終えた状態を見る。同梱の `projects/demo-kb`（社内ナレッジ検索基盤、架空）には
5回分の会議が記録してある。

> 「デモを動かしたい」

`/setup` が、どの案件で始めるかを聞いてくる。`demo-kb` を選ぶ。門（pre-commit）を立て、
`.env` に対象の案件を書き、門を一度通して終わる。

続けて、こう頼んでみる。

> 「今どこ？」

いまの会議（`MTG-20260911`）と、どの段まで済んでいるかが出る。

> 「MTG-20260911 の議事録を出して」

`/minutes` がカードから議事録を組み立てて、会話の中に出す。**ファイルには保存しない。**
カードを直せば、出し直すだけで議事録も直る。`記録なし` や `推測` が隠されずに残っている
ことにも目を向けておく（言語化されなかった量が見えることに価値がある）。

> 「顧客提出版がほしい」

同じ会議の顧客向けの版。役割は社名に、カード ID と逐語引用は消え、推測の決定は落ちる。
落とすのは CLI で、LLM の注意力に賭けていない。

> 「次回のアジェンダを出して」

`/agenda` が出す。冒頭に**理由が未記入の決定**、続いて未完了のアクション、議題が並ぶ。
決着していない議題は、何もしなくても次回に残っている。

ここまでが、これから B で自分の手で作るもの。

## B. 1サイクルを回す：練習用の案件

### B-0. 練習用の案件を作る（5分）

> 「新しい案件を始めたい。案件名は tutorial」

`/setup` が雛形（`templates/project`）から `projects/tutorial` を作り、`role-mapping.yaml` を
**聞き取りで**埋めていく。話者の役割ラベルごとに、所属・決定権・決定の種別を聞かれる。
決定権の無い役割の発言だけでは DEC にならないので、ここが抽出の精度を決める。
**Claude は推測で埋めない**ので、聞かれたら次のとおりに答える。

- 案件名: 勤怠・経費システム改修 ／ 自社: D社 ／ 顧客: C社 ／ 協力会社: なし ／ 会議体: 定例WG

| 役割ラベル | 所属 | 決定権 | 決定の種別 |
|---|---|---|---|
| 顧客PM | 顧客側 | あり | 交渉可能 |
| 顧客担当者 | 顧客側 | なし | |
| 顧客人事 | 顧客側 | なし | |
| 顧客法務 | 顧客側 | あり | 契約制約 |
| 発注元 | 顧客側 | あり | 交渉可能 |
| 開発リーダ | 自社側 | あり | 技術判断 |
| 開発メンバー | 自社側 | なし | |

> 聞き取りを飛ばしたいなら、「demo-kintai の role-mapping.yaml を写して」と頼んでもよい。
> 自分の案件では写さずに答えること。

最後に `kime status` が出て、`.env` が `tutorial` を指す。以降の頼みごとはこの案件に効く。
何を DEC とするかの境界は [`decision-guide.md`](decision-guide.md) にある。自分の案件で
始めるときは、チームで先に読み合わせておく（スキルは読み合わせを代行しない）。

### B-1. 会議の前：議題を起票する（5分）

アジェンダは**議題（AGD）** を骨組みにした、カードの射影。決定・未決・アクションは
どれかの議題にぶら下がり、議題は決着するまで次回へ持ち越される。

![議題が親、DEC・Q・ACT が子。子が「議題」で親を指し、議題は予定会議のアジェンダに載る](docs/images/agenda-structure.svg)

第1回（8月26日）の前に、顧客から3つの「決めたいこと」が出ていたとする。1つずつ頼む。

> 「8月26日の会議で決めたい。『経費精算の承認を何段にするかを決めたい』、提起者は顧客PM」
>
> 「8月26日の会議で決めたい。『打刻をICカードにするかスマホにするか決めたい』、提起者は顧客PM」
>
> 「8月26日の会議で決めたい。『旧システムのデータをどこまで移すかを決めたい』、提起者は発注元」

`/agenda` が聞くのは**文言と提起者の2つだけ**で、言われた言葉のまま議題カード
（`agenda/AGD-001.md` 〜）を起こす。言い換えない・「〜について」に丸めない。
会議の日を言わなければ「次回」に載る。

> 「8月26日の会議のアジェンダを出して」

3つの議題が `未着手` で並ぶ。**アジェンダに手で書き足さない**のがこのキットの約束で、
足したいことは議題として起票する（書き足すと射影でなくなり、次回に残らない）。

### B-2. 文字起こしを置く（1分）

会議が終わったら、文字起こしを `projects/<案件名>/meetings/MTG-YYYYMMDD/transcript.md` に置く。
練習ではデモの第1回を写す。

> 「demo-kintai の MTG-20260826 の文字起こしを tutorial に置いて」

自分で打つならこう。

```sh
mkdir -p projects/tutorial/meetings/MTG-20260826
cp projects/demo-kintai/meetings/MTG-20260826/transcript.md projects/tutorial/meetings/MTG-20260826/
```

形式はこう（デモの冒頭）。

```markdown
# MTG-20260826 定例WG（第1回）

- 日時: 2026-08-26 10:00-10:50
- 会議体: 定例WG
- 出席: 顧客PM, 顧客担当者, 顧客人事, 顧客法務, 開発リーダ, 開発メンバー

---

[00:00:15] 顧客PM: では始めます。今日は議題を3つ出しています。承認の段数、打刻、データ移行です。
[00:00:28] 開発リーダ: よろしくお願いします。
```

- 話者は**役割ラベル**で書き、`role-mapping.yaml` の key と表記を合わせる
- 自分の会議では、音声認識の出力をチャットに貼って「この形式で取り込んで」と頼んでもよい
- **一度コミットした文字起こしと LOG は書き換えない。** すべての引用の照合先なので、
  Claude が編集しようとしても PreToolUse フックが止める

### B-3. 会議の後：取り込む（10分）

> 「会議を取り込んで」

会議 ID は言わなくてよい（いまの会議を道具が知っている）。`/ingest` が次を一続きで進める。

| 段 | スキル | できるもの |
|---|---|---|
| Pass 1 論点に分ける | `/segment` | `meetings/MTG-20260826/segments.yaml` |
| 議題の書き戻し | （機械） | 扱った議題が `未着手 → 継続` に |
| Pass 2 LOG にする | `/log-cards` | `meetings/MTG-20260826/logs/LOG-20260826-NN.md`、未知語の一覧 |
| Pass 3 抽出する | `/extract` | `decisions/` `questions/` `actions/` のカード |
| 引用の照合・lint | （機械） | 一致しない引用は `推測` に降格。error 0 を確かめる |

**人が手を入れるのは、Pass 1 の直後の粒度の確認だけ。** ここで一度止まって、
次のような10行ほどの YAML を見せてくる。

```yaml
segments:
  - seq: 1
    title: 経費精算の承認段数
    種別: 議論
    時刻: "00:00:15 - 00:04:10"
    議題: AGD-001
```

見るのは4つ。直したければ言葉で頼めば作り直す。

1. **粒度** — 1論点 = 1つの問い。分けすぎ・まとめすぎなら「seq 3 を2つに分けて」
2. **種別** — `議論` が `報告` にされていないか（`報告` と `雑談` からは決定を拾わない）
3. **議題** — 論点に付いた議題が合っているか。迷ったものに付いていないのが正常
4. **会議の場で出た議題** — この会議では、顧客担当者が「新しいシステムでは締めを2回に
   分けられないですか」と言い出している。アジェンダに無かった話なので、
   **起票するかを聞かれる。** 「起票する。文言はそのまま、提起者は顧客担当者」と答える

「これで進めて」と言えば、あとは止まらずに Pass 3 まで進む。Pass 3 は**論点を1つずつ**処理する
（一度に渡すと逐語の引用が要約され始め、照合が効かなくなる）。

終わると `kime status` が出て、確認②で判定するものの件数が伝えられる。
このとき、カードにはわざと空欄が残っている。

- **`なぜ` と却下理由は、人が実際に言った言葉だけ。** 無ければ `記録なし`。
  もっともらしい理由の合成が、この仕組みの最大の失敗モード
- **迷ったら DEC ではなく Q。** 「私から聞いておきます」は、問いが Q に、聞きに行くことが ACT になる。決定権の無い役割の
  発言だけでも DEC にならない。嘘の DEC は半年残るが、余分な Q は次回定例で消える
- ACT の担当と期限は、発言に無ければ空欄のまま（空欄が正常な出力）

途中でコンテキストが切れたら「続けて」。済んだ段は飛ばして、残りから再開する。

### B-4. 確認する：空欄を人が埋める（25分）

> 「確認を始めて」

`/review` が該当するカードだけを順に出し、**1件ずつ開いた問いで**聞いてくる。
返した言葉がそのままカードに書かれる。Claude は理由を提案しない（「〜ということでしょうか」と
水を向けると、人はそれを追認してしまうため）。

```
DEC-001「経費精算の承認は課長と経理の2段とする」
  → なぜこの案にしたのですか？（会議で出た言葉がなければ「記録なし」）
ACT-001「部長に月次の一覧送付でよいかを聞く」
  → どこの会社が、いつまでに？
```

| | 内容 | 目安 |
|---|---|---|
| 2-0 | `スコープ: 判定保留` の決定 — 当初の合意に入っていたか（受託開発では最優先） | 3分 |
| 2-1 | 拾い漏れの疑いと `信頼度: 推測` のカード —「実際にそう言われましたか」 | 4分 |
| 2-2 | 決定の `なぜ`、却下理由 | 8分 |
| 2-3 | アクションの担当・期限・状態 | 4分 |
| 2-4 | 制約・前提・用語への昇格候補を yes / no で承認（Pass 4） | 6分 |
| 2-5 | 議題の締め — 決着か、次回も続けるか、取り下げるか | 2分 |

練習の答え方:

- 文字起こしを読んで、**会議で実際に言われている言葉だけ**を返す。無ければ「記録なし」
- 分からないものは空欄のままでよい。`なぜ` が空の決定は次回アジェンダの冒頭に載り続け、
  制約・前提への昇格候補にもならない。それが「書かなかったこと」のコスト
- 2-5 で結論が出なかった議題は「続ける」。開いたまま次回へ持ち越される。
  議題そのものを Q に言い換えない

最後に「lint して」。**error 0 だけが不変条件。** `act-overdue` `q-stale` `why-missing`
などの warning は本当の未達を映す計器なので、消すためにカードを書き換えない。

自分の案件では、**確認は会議当日か翌日に固定する。** 2週間空けると却下理由は思い出せない。

### B-5. 議事録を出す（5分）

> 「議事録を出して」
>
> 「顧客提出版がほしい」

A で見たものが、今度は自分の確認を反映して出る。④で埋めた `なぜ` が載り、
埋めなかったところは `記録なし` と出る。直したいところがあれば、議事録ではなく
カードを直して（「DEC-001 の…を直して」）出し直す。

顧客に送ったら、異議が無ければ確定とみなす定型の一文が末尾に入っている。

> 「議事録を 8月27日に送ったので確定日を書き戻して」

ACT を GitHub Issue にしたいときは「ACT-001 を Issue にして」（`/issue`）。
本文を見せてから、起票してよいかとリポジトリを1件ずつ確認してくる。
**すべての ACT を起票しない**（ACT は会社間の約束で、Issue は自社のタスク。粒度も寿命も違う）。

## C. 2回目の会議：持ち越しと更新

### C-1. 次回のアジェンダを見る

> 「次回のアジェンダを出して」

第1回で結論が出なかった議題が「扱ったが結論なし」、扱えなかった議題が「扱えず」として
残っている。前者は続きから、後者は最初から話す議題。その下に、未決の問いと
未完了のアクションがぶら下がっている。何も書き足していないのに、次回の骨組みができている。

### C-2. 第2回を取り込む

> 「demo-kintai の MTG-20260909 の文字起こしを tutorial に置いて」
>
> 「会議を取り込んで」

B-3 と同じ流れ。違うのは、前回からの続きの話がカードに起きる場面で、
**新しいカードを作らず、既存のカードを更新する**こと。同じ DEC / Q / ACT が複数の会議に
出てくるのは正常で、カードには会議を1つだけ書く欄が無い（会議は根拠の LOG から辿る）。
前回の Q に答えが出れば、その Q が閉じて DEC が生える。

### C-3. 確認して、議事録を出す

> 「確認を始めて」
>
> 「議事録を出して」

2-3 では前回の ACT の状態も聞かれる。2-5 で決着した議題は、閉じた会議の日が `決着日` に入り、
次のアジェンダから消える。

## D. 答え合わせと片付け

### 見比べる

`projects/demo-kintai` には、同じ文字起こしを回して人が確認した記録が入っている。

> 「tutorial と demo-kintai の第1回のカードを比べて」

一致しなくてよい（論点の切り方も抽出も揺れる）。見るのは次の点。

- 決定権の無い役割の発言（顧客担当者・顧客人事）が DEC になっていないか
- 「聞いておきます」「見解が要ります」が Q になっているか
- `なぜ` に、自分が答えていない理由が入っていないか

3つ目が1件でもあれば、それがこのキットが防ごうとしている失敗。

### 片付ける

練習用の案件は**コミットしない。** 門は `projects/` の全案件を lint するので、
置いたままにすると他のコミットまで止めることがある。

> 「tutorial の案件を消して、demo-kb に戻して」

自分の案件を始めるときは、もう一度「新しい案件を始めたい」から。

## スキル一覧

| スキル | 頼み方の例 | すること |
|---|---|---|
| `/setup` | 「セットアップして」「新しい案件を始めたい」 | 門を立て、対象の案件を決め、`role-mapping.yaml` を聞き取る |
| `/agenda` | 「次回のアジェンダを出して」「次の会議でこれを決めたい」 | アジェンダを出す。議題を起票する |
| `/ingest` | 「会議を取り込んで」「続けて」 | Pass 1〜3 を一続きで。粒度の確認で一度だけ止まる |
| `/segment` | 「論点に分けて」 | Pass 1 だけ |
| `/log-cards` | 「LOG を作って」 | Pass 2 だけ（未知語の検出を含む） |
| `/extract` | 「決定事項を抽出して」 | Pass 3 だけ |
| `/review` | 「確認を始めて」「担当と期限を入れたい」 | 確認②の25分を進行する。昇格候補（Pass 4）を含む |
| `/minutes` | 「議事録を出して」「顧客提出版がほしい」 | カードから議事録を出す。確定日を書き戻す |
| `/lint` | 「lint して」「おかしいところを探して」 | 機械の検査に、意味の点検（矛盾・振り分け）を足す |
| `/issue` | 「ACT-001 を Issue にして」 | Issue の下書き。起票は確認してから |

`/ingest` は `/segment` `/log-cards` `/extract` を順に呼ぶ束ね役で、判定基準はそれぞれの
スキルにしか無い。パスを1つだけ回したいときは直接呼ぶ。

## 困ったとき

| こんなとき | こう頼む |
|---|---|
| どこまでやったか分からない | 「今どこ？」 |
| 途中で切れた | 「続けて」 |
| 文字起こしや LOG を直そうとして止められた | 直さない。不変層で、すべての引用の照合先。カードのほうを直す |
| 引用が一致しないと言われた | 「引用を照合して」。一致しないものは `推測` に降格する（LOG は直さない） |
| 知らない役割ラベルが出てきた | 粒度の確認のときに言われるので、所属と決定権を答える |
| warning が多い | そのままでよい。error 0 だけが不変条件 |

## 付録

### Obsidian で読む

**案件のディレクトリ（`projects/<案件名>`）を vault として開く。**
`/setup` が `projects/<案件名>/.obsidian/` に事故防止の設定（ファイル名変更時に内部リンクを
自動更新しない）を置く。カードの参照（`議題: "[[AGD-001]]"` など）とビューの ID はリンクで書かれるので、
バックリンクとグラフで決定・議題・根拠の LOG を辿れる。詳しくは [`docs/obsidian.md`](docs/obsidian.md)。

### スキルを使わずに打つ

スキルは CLI の `kime`（`python3 tools/kime.py`）を呼んでいる。サブコマンドの一覧は
`python3 tools/kime.py`、各サブコマンドの使い方は `python3 tools/kime.py <サブコマンド> --help`。
対象の案件は `.env` の `CURRENT_PROJECT`、または `--root` で指定する。
`--meeting` を省くと最新の会議（`kime status` の「いまの会議」）。

```sh
sh tools/setup.sh demo-kb                   # デモで始める
cp -r templates/project projects/<案件名>    # 自分の案件で始める
sh tools/setup.sh <案件名>
```

### ファイルの地図

| 場所 | 内容 |
|---|---|
| `projects/<案件名>/` | 案件ごとのカード群と `role-mapping.yaml` |
| `projects/<案件名>/meetings/MTG-*/` | 文字起こし・論点・LOG（**不変層**） |
| `projects/<案件名>/views/` | 生成物。**手で編集しない** |
| `ontology.yaml` | 型・フィールド・語彙・閾値の唯一の正本 |
| `decision-guide.md` | 何を DEC とするかの判定ガイド。**最初に読む** |
| `schema.md` | カード定義の論証（型一覧・ID 形式・フィールド表・導出表は `ontology.yaml` から生成） |
| `templates/` | 案件とカードの雛形 |
| `.claude/skills/` | 各パスの手順と判定基準。`ingest` は束ね役で、順序と止まる場所だけを持つ |
| `CLAUDE.md` | 3つの層と、絶対に守る3つのルール |
| `docs/design.md` | 設計の根拠・期待値の較正・判定基準・既知の難所 |
| `docs/backlog.md` | やらないと決めたことと、その理由 |

案件ディレクトリに `.fixture` を置くと教材として、`.wip` を置くと作りかけとして自動検査から外れる。
作っている途中は error が出て当たり前なので、`.wip` を置いて作り、error 0 になってから外す。

門は `.githooks/pre-commit`（テスト・生成物の鮮度・lint・不変層の5段）と、
同じものを `--all` で呼ぶ CI（`.github/workflows/checks.yml`）の二重。
clone しただけでは git は `.githooks` を見に行かないので、最初に `/setup` を通す。
